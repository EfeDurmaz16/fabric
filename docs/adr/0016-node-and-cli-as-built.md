# ADR 0016: The node and the CLI as built

Status: accepted, 2026-10-20

Records `crates/fabricd` (the node) and `crates/fabric` (the command), branch `feat/daemon-cli`. Answers the open questions of ADR 0013 about the node crate, decides the ADR 0003 open question about departed copies, and names where the build departs from ADR 0001, 0003, 0004, 0008 and 0011, and why. Everything not named here stands as those ADRs say.

## Context

The core, the store, the network layer, the harness adapters and the environment crate existed as libraries. Nothing joined them: no process held the store, no file held a ledger, and no command moved a job. The architecture page planned two crates, `fabric-node` and `fabric-cli`. They are `fabricd` and `fabric`, so the binary is `fabric` and the daemon library has the name a reader expects of a daemon.

## Decision

### One process per state directory

`fabric serve` runs the node. It takes an exclusive `flock` on `<state>/daemon.lock` before it opens anything, and keeps it for its whole life. The state directory is `$FABRIC_HOME`, else `~/.fabric`, mode 0700. A missing one is created 0700, the last step by a plain `mkdir`, so a link that takes the name after the start looked fails it instead of being followed. An existing one must be the user's and must be the directory itself, not a symlink to one, however the path is spelled: whoever owns the link could point it elsewhere while the node runs, and the CLI refuses a linked state directory too. Every entry at its top must be the user's as well, judged as itself, so a link is its maker's, at every start and whatever its mode: an entry another user made while they could write there, such as a `peers` book that pairs their node, is still theirs once the directory is narrowed. When the directory lets others in, its mode is narrowed only if it also holds nothing but the entries below and logs (`*.log`), which a user who sends the daemon's output there makes before the first start, so a `FABRIC_HOME` that names `/tmp` or a project directory is refused and left as it was. One others can write is narrowed before its entries are judged, so none can be added after the check, and gets its mode back when it is refused. Only the top level is judged by owner; a file of the user's that others could write, such as a group-writable `harness.toml` in a directory shared with a group, is the user's to check:

```text
<state>/
  daemon.lock   node.key   peers   peers.lock   harness.toml (optional)   fabric.sock
  store/        the store of ADR 0014
  locks/        one tree lock per workspace root, so one installer runs per tree (ADR 0007)
  harness/      the adapters' departure records and Claude config lock, always under ~/.fabric (ADR 0015)
  jobs/<job-id>/
    ledger      append-only records (ADR 0002)
    manifest    the derived job manifest
    marker      what the workspace at the root holds, and the epoch it was written at (ADR 0004)
    harness     the harness this node launched: pid, kernel start time, epoch
    session     the harness session the job continues here
    session.pending  a registration's session, until the Resumed after it is durable
    fresh-codex  the Codex threads the workspace held when a Codex with no thread to resume was planned here
    env-spec-ran  the spec id and install inputs whose setup steps the user approved here, written by the CLI, removed by a restore of another node's snapshot (ADR 0007)
    secret-patterns  every secret pattern the job's spec held at a capture here (ADR 0004)
    harness-state/   capture output and restore input for the adapter
```

The node is the store's single writer, the ledger files' single appender and the supervisor of every harness it recorded. There is no mode in which the CLI takes the lock itself: without a daemon every job command fails with "no fabric daemon ... start one with `fabric serve`". ADR 0003 allows the `resume` command to be the supervisor when no node runs; that path is not built.

The control socket is `<state>/fabric.sock`. One connection carries one request and one response, each a `u32` length and postcard bytes. A path of 104 bytes or more is refused at start with a message, because macOS cannot bind it. The mode of the state directory is not the only check: the daemon refuses a connection whose peer user id is not its own, and the CLI refuses a state directory or socket another user owns, or a directory others may enter, before it trusts a run plan read there. The daemon reads `harness.toml` once at start, and every run plan carries that copy's entry for the harness it launches, and no other, so the plan's size does not grow with the file and the CLI launches a harness under the configuration the daemon captures and restores it with; an edit to the file takes effect when the daemon restarts. The plan carries the daemon's resolved home too, and a CLI whose `HOME` resolves to another directory, with the same `FABRIC_HOME`, refuses the launch before any setup step, since the harness would keep its session under a home no suspend reads (Codex review, 2026-10-21).

### The ledger file

`LedgerFile` implements `LedgerStore` as ADR 0002 specifies: one `write` of the whole record, `F_FULLFSYNC` on macOS and `fsync` elsewhere, the first record written to a sibling, flushed and renamed into place with the directory flushed, so a failed first write leaves no ledger rather than an empty one, and a `Created` for another job is refused before any file is made. A failed append is cut off again; if that fails too, the file refuses further appends until the node restarts. Open truncates a torn tail and fails closed on any other damage, leaving the file byte for byte as it was. A manifest that remembers more records than the ledger holds fails closed with `BehindManifest`. ADR 0002 chose a file over SQLite; this build keeps that choice.

The node-local files beside the ledger, `marker`, `harness`, `session`, `session.pending`, `fresh-codex` and `forked`, are JSON, each replaced whole by a durable rename; `env-spec-ran` is one line of text the CLI replaces the same way. They never travel to a peer and never decide ownership, so they need no stable binary form, and a user who reads one by hand while a job is frozen can tell what it says. The ledger, the manifest and everything on the wire or the control socket stay postcard.

### Who does what

The CLI never touches the store or a ledger. It sends a request, prints the lines the node answers with, and for `run` and `resume` does what only it can: it runs the setup steps of ADR 0007 in the user's environment under the tree lock in `<state>/locks`, held from the plan until the node has answered the harness's registration, after it prints them and asks, unless given `--yes`, when this node has not run that spec over those install inputs for the job (ADR 0007, step 4; with no terminal to ask, the answer is no), launches the harness in its own process group with the user's environment, gives the terminal to that group when the harness is interactive, and registers it. The node appends `Resumed` only if it still owns the job at the epoch the plan was made under; otherwise the CLI kills the group at once. A plan can be overtaken before the CLI takes the lock: another launch can register its harness and let the lock go in between. So under the lock, before the first setup step, the CLI asks the node again (`LaunchCheck`), which refuses when it no longer owns the job at that epoch, records a harness that runs, or holds records past the ledger head the plan carries, so a launch that registered and exited in between, and wrote its session, also overtakes the plan (Codex review, 2026-10-21). When the harness exits, the CLI tells the node. The CLI catches `SIGINT`, `SIGHUP` and `SIGTERM` from before the launch: one that arrives before the node recorded the harness stops it, one after leaves it running under the node, and one while the CLI waits to tell the node of the exit ends that wait, since the node answers only once it holds the job, which a suspend or a move can keep for minutes. Each ends the command with 128 plus the signal. When a signal cuts a registration the node goes on to record, the harness it records was stopped before it wrote its session; the next capture finds no state for a session this node never captured or restored, forgets it and carries no harness state. A Codex launched with no thread to resume makes its thread only once it runs, so its registration names none. The plan of such a launch notes in `fresh-codex` the threads whose rollouts record the job's root as their `cwd`, and the next capture or plan takes the oldest thread outside that note as the job's and records it: an older one is the job's from before, as a thread from a Codex run before the job switched to Claude, and a newer one was made by something the launch ran, a `codex exec`, a sub-agent or a review. With no such thread, or no such plan since the job last arrived, the record stands, so a Codex that never got past its login screen leaves the Claude session in the snapshot. A user who starts another conversation inside that Codex, as with `/new`, keeps the first one with the job, as a Claude `/clear` keeps the session the launch named (second review of 2026-10-22). The node registers only a pid that leads its own process group, read with `ps`, so a headless harness that finished its turn and exited before the CLI registered it, and that the CLI has not reaped yet, still counts; its record stands for that group: it stays while a process the harness started still runs in the group, a stop signals the whole group and returns only once the group is empty, and a group that cannot be signalled or outlives `SIGKILL` fails the suspend, the move or the fence with the record kept. So does a group whose leader's start time `ps` could not read: only `ps` exiting 1 with no output counts as no such process, and any other failure leaves the group unsignalled, since its pid may have been given to another process (Codex review, 2026-10-21). A process that leaves the group, with `setsid` for one, is out of reach.

ADR 0007 has the caller take the tree lock before restore writes the tree. Here the node restores and the CLI materializes, so the lock is taken after the restore. The restore writes only into an empty directory it renames into place (ADR 0014), so it never writes over a tree that an installer from an earlier `resume` still holds; that `resume`'s lock makes the next one refuse with the lock's path. A suspend, which a `move` and a peer's pull also run, takes the same lock before it stops the harness and holds it until the snapshot is recorded: while a `run` or `resume` is in its setup steps or has not yet registered its harness, or a setup step it started still runs, there is no harness to stop, and a capture would publish a tree an installer is still writing, so the suspend refuses with `SetupRunning` instead (Codex review, 2026-10-21). A process a setup step left running with the lock as its input, such as a daemon that did not redirect it, holds the lock until it exits, so suspends and moves of that job refuse until then. The refusal names the lock file, so `lsof` finds the process; a peer's `steal --force` is the way out that does not wait for it. Recording the step's process group next to the lock, which ADR 0007 already names for an installer killed under a running build, would let a suspend tell a leftover process from a live installer; that is not built.

The harness gets the user's environment minus the parent-session markers ADR 0015 lists, so a `fabric job run` typed inside a Claude Code session starts a session of its own. Before a Claude launch the CLI pre-seeds trust (ADR 0006, amended for gate finding F1) and never fails on the outcome: it prints nothing when Claude's key for the workspace was already set, `trusted <key>` when it wrote the key, and a one-line warning when it left the file alone, such as while another `claude` runs. The node confirms the adapter's capture with `confirm_departure` once `SnapshotPublished` is durable, on the first suspend and on the one that finishes it after a crash, so the departure record of ADR 0015 counts only for a published snapshot.

Interactive launches give the terminal to the harness with `tcsetpgrp`. The CLI never takes it back; the shell does when the command exits, as it does for any job.

### Exit codes

A refusal crosses the control socket with its kind next to its text, so the CLI picks its exit code from the kind and never parses the text. Scripts and the triggers of ADR 0008 read these:

| Code | Meaning |
|---|---|
| 0 | Done; for `run` and `resume`, the harness exited with 0 |
| the harness's code | The harness exited with that code |
| 128 + signal | The harness was stopped by that signal, as when the node fences it; a line names the signal and the status command |
| 80 | No daemon answers on the control socket |
| 81 | Not the owner: another node owns the job, this node does not know it, or the plan's epoch is over |
| 82 | Frozen: a move this node started waits for its target, or the job is frozen after a fork |
| 83 | A peer could not be reached, or gave no answer in time |
| 84 | Refused without `--force`: the preflight, or a steal's dry run; or without `--yes`: setup steps this node has not run for the job over these install inputs, or not since the workspace came from another node, not approved (ADR 0007) |
| 85 | The job's state stops the command: a suspend or restore to finish, a harness that runs or another `run` or `resume` of the workspace still starting one, a workspace an earlier tenure left, no snapshot, a run during a move |
| 1 | Any other failure; 2 is a usage error from the argument parser |

A harness that exits with a code from 80 to 85 cannot be told from a refusal by the code alone; none of the supported harnesses does.

### Job roots and departed copies

`fabric job new --repo <path>` clones the repository into `~/fabric/jobs/<job-id>/work` (ADR 0011, rule 2). The node makes `~/fabric/jobs/<job-id>` mode 0700, there and when a restore makes it, since the workspace holds what the agent writes, ignored secrets included; a directory that already exists keeps its mode (Codex review, 2026-10-21). `fabric job init`, which adopts a checkout in place, is not built; ADR 0001's statement that `init` is the only way a job starts is superseded by `new` for this phase.

A restore lands at the root the snapshot recorded only when that root is exactly `~/fabric/jobs/<job-id>/work` under this node's home, because the root arrives from a peer and any other path, such as `~/.ssh`, is a bug or a hostile peer. When it is not, the job lands under `<state>/jobs/<job-id>/work`, and the CLI prints why. The adapters of ADR 0015 still refuse a different root or home, so only a harness without path-keyed state can continue there; doctor refuses the move before it gets this far.

A clean marker also records a stamp of the tree: a hash of every path under the root and each file's size, mode, inode, modification and change times, leaving out `.git/objects` and `.git/refs/fabric`, which a capture writes itself. A suspend measures it before it captures and a restore after it writes the tree. A user can edit a clean workspace by hand, or run a harness in it that Fabric did not start, so a marker counts as clean only while the tree still measures its stamp. A suspend that finds the stamp changed captures again instead of answering "already suspended", which covers the suspend inside `job move` and inside a holder's answer to a pull; and the source of a push measures again before `MoveStarted` and stops the move when the tree changed while the target copied it.

ADR 0003 kept a departed copy at the root as a warm cache and left open whether it should move. It moves. When a node learns that the job departed, or was stolen from it, and its marker says the workspace is clean at a published snapshot and the tree still measures its stamp, the workspace is renamed to `departed/<epoch>` beside the root and kept. Nothing in it is missing from the job, a user who types `claude` in the old directory finds nothing there, and two nodes that share a disk, as the end-to-end test does, never meet at the root. A workspace with changes made after its last snapshot stays where it is, and `status` names it an orphan; nothing deletes it.

A node can lose a job while its marker says live, keep that orphan, and own the job again later at a higher epoch, by a pull, a push toward it or a steal. So the marker records the epoch this node held the job at when it wrote it. A restore reuses the workspace at the root only when its marker was written at the current epoch, or was restoring exactly the latest snapshot, or holds it with the tree unchanged since. Any other workspace is renamed to `orphan/<epoch>` beside the root, `<epoch>` being the marker's, with `.1`, `.2` and on added when that name is taken; a harness still recorded from that tenure is stopped first, the session record it continued is forgotten, a line names where it went, and the latest snapshot is restored fresh. Every fresh restore forgets the session record, so the job continues the session the snapshot carries or starts a new one. `run` refuses such a workspace and names `resume`, and `suspend` does not capture it. The in-place restore of ADR 0004, which updated a departed copy, is therefore not needed and not built: every restore is the fresh restore of ADR 0014.

### The move as built

The push (`fabric job move <job> --to <node>`, typed on the owner) follows ADR 0003 step by step: preflight, suspend, push the ledger with `Append` (the target fetches the latest snapshot over the same session before it answers the last page), `MoveStarted` made durable, `Append` again so the target holds it, `MoveOffer`. The target answers with the one decision for that move id, durable before the answer leaves. The job's lock is released while the target copies, so before `MoveStarted` the source checks again that the job is suspended in the snapshot it pushed and that no run was planned since; a `run` planned marks the workspace live, and a move that finds it so stops with the job still owned here. A lost answer is followed by `MoveStatus` on a fresh connection; five failed tries leave the source frozen and say so with the one command that resolves it.

The pull (`fabric job resume <job>` on a node that does not own the job) fetches the records, runs the preflight against the harness that will launch here (the `--harness` override, or the job's own, read from the fetched records when the job is new here), fetches the snapshot, sends `MoveRequest`, and the owner suspends (stopping its harness) and appends `MoveStarted` toward the puller. The puller fetches again, decides the offer from its own replica with `Ledger::answer_offer`, and pushes the `MoveImported` back. `--on <node>` names the node to pull from when this node has never seen the job; otherwise the ledger's owner is used. A pull never moves the job to a third node: resume means here (ADR 0008).

`fabric job steal <job> --force` writes `Stolen` and a `Note` with the warning; without `--force` it prints what it would do and fails.

Three protocol details the earlier ADRs left open:

- A node that holds none of a job's records sends `Pull { after: None }` and gets the chain from `Created`. An `after` the answering chain does not hold is answered `NotInChain { head }`: the asker stops when its own chain holds that head, because the peer is only behind, and otherwise the chains forked and the node acts as Forks, below, says.
- A record a peer sends is checked first as the peer's own. If the ledger says another node wrote it, it is accepted as relayed (ADR 0002, amendment 6), except when the writer is this node: a node writes its own records and never learns one from a peer.
- A per-job request whose epoch is behind this node's is answered `StaleEpoch`, checked under the job's lock, except `Pull` and `MoveStatus`, which are reads: the asker of a pull is catching up, and the source asking for a decision is one epoch behind once the target imported. A `MoveRequest` or a `MoveAbort` whose epoch is ahead of this node's is answered `AheadOfUs`, since this node must catch up before it acts. A `MoveAbort` is accepted only from the move's source, and one for a move already decided is answered with the decision at any epoch.

### Recovery and catching up

A node catches up with its paired peers at start, whenever a session with a peer begins, and before a `run` or a `resume` of a job it owns. Catching up pulls each job's records from each peer the node can call, one with a pasted address or one that holds a session open with it, then settles the job: it kills a harness whose epoch is over and moves a clean departed or stolen-from copy aside.

At start each peer is caught up on a task of its own, so the pass takes about one dial however many peers there are, and a peer that does not answer costs one failed dial for the whole pass rather than one per job (about 13 s with QUIC then TCP). The target of an open move is then asked for its decision, unless it did not answer. A session that begins while the pass runs, such as one an addressless peer opens after the pass listed the peers it can call, is caught up when the pass ends. That holds for a peer the pass already caught up with too, since the peer may have written a steal after its catch-up and before its session began. Until 2026-10-21 such a session was dropped, so the steal stayed unknown until the next session or run. The same holds after start: a session that begins while a catch-up of its peer still runs makes that catch-up run once more when it ends, since the running one may have pulled a job before the peer wrote to it, or wait on a session that died, which an addressless peer cannot be dialled to replace. Commands that change a job wait until this pass has run; `job ls`, `status` and `log` answer from local state at once, never dial, and say so while the pass still runs. Node commands and doctor do not wait.

Before a launch each reachable peer gets three seconds; one that does not answer is named and the run goes ahead on this node's ledger, and so is a paired peer this node cannot ask at all, with no address here and no session open. So a node that slept through a steal does not launch the stolen job when it reaches the thief at its start or at the check before the run. When it cannot reach the thief then, as when the thief has no address here and has not opened a session since this node started, or does not answer, it launches its own copy, and the two run until the nodes meet: at a later check, when either side opens a session, or at the next start (an open question, below). A node that stays up while the thief is out of reach, as a laptop on another network, keeps its harness running until the two meet the same way. The Fencing section of ADR 0003 already accepts that a harness edits until its node learns the epoch.

### Forks

The fork rule of ADR 0003 is not built, so a node fails closed instead. When a peer's ledger for a job does not continue its own and the peer's ledger reached an epoch at least as high, the node writes `jobs/<job-id>/forked` with the peer, that epoch and the peer's head. It finds this when a pull is answered `NotInChain` with a head its own chain lacks, after which it reads the peer's whole chain for the epoch, or when a page a peer pushes at an epoch at least as high does not link to its head. From then on the job is frozen on that node: `run`, `resume`, `suspend`, `move`, `steal`, `approve`, `reject` and a peer's move request refuse it, the recorded harness is stopped, the workspace stays where it is as an orphan, and `status` names the peer to continue on. When the peer's epoch is lower, the peer is the side that freezes when it learns this node's records, and this node carries on. Nothing lifts a freeze; the fork rule will. The peer's epoch is read from its records as they arrive, so a paired peer that lies can freeze a job here but cannot make this node run one.

### Doctor

`fabric doctor` prints this node's facts; `fabric doctor --peer <node> [--job <id>]` compares them with the peer's, row by row as ADR 0008's table lists them. `job move` runs the same comparison first with the peer as the target, and a pulling `job resume` runs it with this node as the target; both take `--force`. A peer's facts arrive in a new request, `RequestBody::Facts`, so the protocol version is 2. A node measures its facts with the `PATH` its daemon started with; this node's side uses the `PATH` of the CLI that asked. One row is not in the table: `git.version`, measured on the daemon's own `PATH` on both sides because restore runs git there, refuses with no waiver when the target has none and a job is named, since every job's workspace is a repository (Codex review, 2026-10-21); the versions may differ. Nor is `lsof`, where the node finds the `lsof` Codex capture runs: every suspend or move of a Codex job asks it whether a Codex process holds the thread's rollout open and fails without it, so the row refuses a Codex job with no waiver when the target has none, warns when no job is named, and is equal for any other harness (review of PR `feat/daemon-cli`, 2026-10-22). Three rows depart from the table: the clock row warns above 5 s and never refuses, because a carried cache whose mtimes are off only rebuilds; the CPU and operating system rows warn; and the network row reports the wire without a refusal, since a dial that fails stops the move anyway. The comparison is not yet written into the job record next to the move.

`--force` waives every refusal except a different user or home and a target without a login for the job's harness, as ADR 0008 says, and the rows added since that the target could not run or release the job without: no git, no `lsof` for a Codex job, and for an ACP job no agent on the pulling command's `PATH` or no `state_dir` for it in `harness.toml`. The step 1 brief asked that `--force` waive every row; the ADR's two exceptions are kept, because the result would be a root that does not exist on the target, and so are the later ones, because the target would own a job it cannot launch, restore, capture or move.

### Where a root may not live

The root is refused under `~/Library/Mobile Documents` everywhere, and under `~/Desktop` or `~/Documents` on a node where iCloud syncs them (`defaults read com.apple.finder FXICloudDriveDesktop`). ADR 0011 also refuses `/tmp`. That rule is not enforced: roots are always under the home, the end-to-end test puts its home under `/tmp` to keep the socket path short, and on Linux every temporary directory is there.

### Carry keys

Capture measures carry keys with `fabric-env` detection: a cache detection does not know is `Unmeasured` and never carried. A workspace whose detection fails, such as a `.fabric/env.toml` that does not parse, is not captured: the suspend stops and names the error, because the target would take the job and then fail to materialize it. A restore cannot run detection before the workspace exists, so it measures the key of the same shape as the source's: the same package manager, its own versions and paths. Each cache prints one line, carried or rebuilt and why.

Capture also stores the spec detection made as an object of the store and names it in the snapshot's `env_spec`, and takes as the job's recorded secret patterns those of `jobs/<job-id>/secret-patterns` joined with those of the spec the job's latest snapshot names, so the patterns travel with the job (ADR 0007, amended 2026-10-22).

### Decisions as ledger events

`fabric job approve` and `reject` append `DecisionRecorded { text: "approved" }` or `"rejected"`, with the user's note after a colon. ADR 0002 makes a new event kind a format version bump; a typed approval record waits for the UI that would read it.

### The network questions of ADR 0013

- The node owns the `Service` implementation. The store gained `Store::manifest_chunks` and `ObjectStore::read_stored` so the node can serve without reading the catalog's internals.
- The peer book holds only the addresses the user pasted at pairing. `seen` records the time of a successful dial and no address, and is never called for an accepted connection, whose source address may sit behind a NAT. Which side can dial is therefore the presence of a pasted address.
- `Endpoint::with_dial_order` takes `QuicThenTcp`, `QuicOnly` or `TcpOnly`; `fabric serve --wire` sets it.

### Fault points

`fabricd` has a `faults` feature, on only in the end-to-end test's build. With it, `FABRIC_FAULT=<point>[:<action>]` arms one of `after_quiesce`, `after_snapshot_publish`, `after_departing_write` (on the source of a push, or on the holder answering a pull), `mid_transfer`, `before_import` (on a pulling node that holds the `MoveStarted` toward it) and `after_import_receipt`, with `crash` (stop, write the signal file, wait for `SIGKILL`), `stall` (two seconds), `hold` (until the test removes the signal file), `drop` or `dup`. A point fires once per daemon process. The value is read once at start, and one that names an unknown point or action stops the node there. Without the feature the functions are empty and nothing reads the environment.

## Alternatives considered

1. **The CLI as supervisor when no daemon runs** (ADR 0003). Two code paths for every job command, one of them holding the store lock for as long as a harness runs. Deferred; the daemon is cheap to start and the gate runs one on each Mac.
2. **Keep the departed copy at the root and build the in-place restore.** The copy is a warm cache only for git objects the bundle chain already carries, the in-place restore is the most dangerous code ADR 0004 describes, and a copy at the root invites a by-hand resume of a departed session. Rejected for this phase.
3. **A JSON control protocol.** Easier to read with `socat`, but the request types already serialize with postcard, and a second encoding for messages that cross between two programs is a second thing to keep in step. Rejected. The node-local files are JSON for the reason The ledger file gives: one program writes and reads them.
4. **SQLite for the ledger.** ADR 0002 rejected it; nothing in the build changed the reasons.
5. **A new event kind for approvals.** A format version bump for a record no code reads yet. Deferred.

## Consequences

- The first gate can be run by hand: build on the Pro, copy the binary to the Air, `fabric serve` on both, pair, `job new`, `run`, `move --to`, `resume`. The README's quickstart is that sequence.
- `fabric job move` and a pulling `fabric job resume` suspend the harness on the source: a pull from a node where the harness runs stops it there.
- Tests: the ledger file's torn tail, damaged middle record, manifest ahead of the ledger and a writer killed with `SIGKILL` mid-append; a reused pid; the doctor table row by row; the root rules; carry key comparisons; and the end-to-end test, which runs two daemons over loopback on QUIC and on TCP+TLS, moves a job and back, breaks the push at each fault point and the pull on the holder after its `MoveStarted` and on the puller before its import, with `SIGKILL` of either daemon or a dropped or duplicated answer, and asserts after recovery that both ledgers name one owner at one epoch, the departed copy refuses to run, and the owner resumes the workspace and the harness session whole. With a fake agent that stays alive after its turn it asserts that a push, a pull and a steal stop the harness on the node that loses the job, that a run during a move's transfer stops the move, and that a node whose ledger forked freezes the job, whether the steal reached it at once or at its next run.

## Open questions

- Should a node that cannot reach the target of its open move offer the user `fabric job move --abort`, which ADR 0003 describes and this build does not have?
- `fabric orphan export` (ADR 0003) is not built; an orphan workspace is reported, or set aside under `orphan/<epoch>` by a restore, and never deleted.
- A CLI killed after it launched the harness and before the node recorded it leaves a harness the node does not know, so no suspend, move or fence stops it. Should the node launch through a small supervisor it owns, or the CLI record the pid in the state directory before it registers?
- A node that cannot ask a paired peer before a launch launches on its own ledger, so a steal that peer made while this node was down runs beside this node's copy until the two meet. Proposal: `job run` and `job resume` refuse with exit 84, waived by `--force`, when the job's ledger names a peer that has no address here and has opened no session since this node started, which blocks only the jobs that peer could hold. `job run` takes no `--force` today, so the waiver needs a field in its control request, which the client API of PR #13 replaces. Decide with that PR, before the gate.
- The fork rule of ADR 0003 is not built: a node whose ledger forked after a steal, at an epoch no higher than the peer's, freezes the job (Forks, above) until the rule exists.
- The store applies its own secret list, not `fabric_core::secret` (ADR 0004, integration note of 2026-10-20).
- How do two nodes find each other after a network change? On the gate (finding F3, 2026-10-20) the Pro moved to another subnet overnight and the Air's address was unreachable from it. Today the user re-pairs with `fabric node add` and a new address. Candidates: Tailscale as an optional underlay whose addresses survive the change, or the reachable side dialing a rendezvous. Decide after the first move on the gate.
