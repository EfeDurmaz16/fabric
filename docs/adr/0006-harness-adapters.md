Status: accepted, 2026-10-19

Amended 2026-10-20 after the first implementation (`crates/fabric-harness`, branch `feat/harness`) and its reviews: the trait section is superseded by [ADR 0015](0015-harness-trait-as-built.md), and four statements of fact are corrected in place.

Amended 2026-10-19 after step 1 research. The trait did not change. References to the root rule now point at ADR 0011.

## Context

The agent that does the work changes weekly. Claude Code keys resume to a working directory (claude-code #5768, #28745, cited in `2026-10-19-t3code-vs-fabric.md`, section 2). Codex exposes `thread/resume` through its app-server JSON-RPC. T3 Code, when it hands off, starts a fresh provider session fed with text and loses tool state and pending approvals (same note, section 1). The Agent Client Protocol (ACP) now has adapters for both: `zed-industries/claude-agent-acp` and `agentclientprotocol/codex-acp` (agentclientprotocol.com, agents list, checked 2026-10-19), with `session/new`, `session/load` gated by the `loadSession` capability, `session/prompt` and `session/cancel`.

Fabric's core must not know any of this. If it does, every vendor release is a core release.

## Decision

### The `Harness` trait

Superseded on 2026-10-20 by [ADR 0015](0015-harness-trait-as-built.md), which records the trait as built: where it lives, its six methods, the manifest, and the restore rule. Three parts of the original text still hold.

- `HarnessKind = ClaudeCode | Codex | Acp { program: ProgramName, args: [String] }`. The program is a bare name (no slash, no NUL or other control character, no leading `-`, not empty) looked up on `PATH`, never run through a shell (review amendments, 2026-10-19).
- The harness is chosen at runtime from the ledger (`--harness codex` on a job created under Claude Code), so the core holds a `Box<dyn Harness>`, and the methods return `BoxFuture`, defined in `fabric-core` (ADR 0005), because native `async fn` in a trait is not dyn compatible on the pinned toolchain. The core stores what `capture` produced as the `harness_state` tree of the snapshot (ADR 0004) and never opens it.
- The process that calls `launch` is the `fabric resume` CLI, which passes the user's own environment minus the parent-session markers of the F2 amendment below, so a daemon's environment never leaks into a harness. Corrected 2026-10-22 after a Codex review: this line used to filter that environment to the names the `EnvSpec` lists plus `HOME`, `PATH`, `TERM`, `SHELL` and `LANG`. That filter was never built, and it would drop what the harness and the builds it runs need and no spec declares, such as `ANTHROPIC_API_KEY`, `HTTPS_PROXY`, `CODEX_HOME`, `JAVA_HOME` or `SSH_AUTH_SOCK`, while a name `.fabric/env.toml` lists is required on every node (ADR 0007). The harness runs as the user who typed the command, with that user's variables (ADR 0016, Who does what). Keeping a variable from it would be a decision of its own, with its own list.
- Amended 2026-10-20 (gate finding F2). On the first gate run a `claude` started from inside a Claude Code session reported transcript saving off because of an inherited `CLAUDE_CODE_CHILD_SESSION` marker, so the job left no transcript to resume. Every adapter therefore spawns its harness, Claude, Codex or ACP agent alike, with the environment the caller passed minus a denylist of parent-session markers, kept in one module (`crates/fabric-harness/src/markers.rs`) whose doc cites the evidence. The rules were split by evidence on 2026-10-20 after review, from the Claude Code 2.1.294 bundle (the environment it builds for every process a session starts, and its list of the variables it sets on its own shells) and the environment of a Claude desktop session, names only. Always left out, because only a host sets them and they say whose child a process is: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_HOST_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_INVOKED_SKILLS`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `AI_AGENT`, `CLAUDE_AGENT_SDK_*`, `CLAUDE_PREVIEW_*`, the host-owned names the same bundle reads at startup to classify the session or forbids a settings file to set (added after a second review, 2026-10-20: `CLAUDE_CODE_REMOTE_SESSION_ID` and `CLAUDE_CODE_CONTAINER_ID`, which make the child a remote or container session, `CLAUDE_CODE_SANDBOXED`, which makes it skip its trust check, `CLAUDE_CODE_REMOTE_TOOLS_HOST_ALLOWS_UNATTENDED`, a host's grant, `CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH`, `CLAUDE_CODE_TOOL_USE_ID`, and the host worktree, scheduled run, cowork, skill, artifact, SDK and Chrome names; the full list is in `markers.rs`), and the markers Codex sets on the processes its tools start (`CODEX_THREAD_ID`, `CODEX_TOOL_CALL_ID`, `CODEX_SESSION_ID`, `CODEX_VERSION`, `CODEX_PERMISSION_PROFILE`, `CODEX_APPLY_PATCH_PRESERVE_LINE_ENDINGS`, read from openai/codex at `e4568a3`). Left out in any Claude host session, shown by `CLAUDECODE` or `CLAUDE_CODE_ENTRYPOINT`: `TRACEPARENT` and `BAGGAGE`, which would join the child to the parent's trace, and `GIT_EDITOR`, `GIT_CONFIG_PARAMETERS` and `BUN_OPTIONS`, which the host sets for its tool shells. Left out only under the desktop host (`CLAUDE_CODE_ENTRYPOINT=claude-desktop`): every `CLAUDE_CODE_*`, `ANTHROPIC_BASE_URL`, `MCP_CONNECTION_NONBLOCKING` and `MCP_SERVER_CONNECTION_BATCH_SIZE`, except, after a second review on 2026-10-20, the user's own login and provider settings under `CLAUDE_CODE_` (`CLAUDE_CODE_OAUTH_TOKEN`, the client certificate names, the Bedrock, Vertex, Foundry and other provider switches with their skip-auth names, `CLAUDE_CODE_MAX_OUTPUT_TOKENS`), which the observed desktop environment did not carry and some of which hold a secret a settings overlay cannot. Any other user `CLAUDE_CODE_*` setting is still lost under the desktop host and belongs in an overlay's `env`. The desktop host points `ANTHROPIC_BASE_URL` at an endpoint it chooses, switches features of the child with `CLAUDE_CODE_*`, and lets a headless turn start before its MCP servers connect; a terminal `claude` sets none of these, so under it a user's own gateway URL and `CLAUDE_CODE_USE_BEDROCK` pass. Kept: the user's configuration (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `HTTPS_PROXY`, `PATH`, `CODEX_HOME`, `MCP_TIMEOUT`) and Codex's confinement markers (`CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED`, the network proxy variables), because the sandbox and the proxy they describe pass to every descendant, so they stay true for the child. Names left out are logged at debug level, never values.

### ACP is the generic path

Any agent that speaks ACP and reports `loadSession: true` gets the `Acp` adapter for free:

- `stop`: send `session/cancel` if a prompt is in flight, then end the agent process.
- `capture`: record the ACP `sessionId` and copy the agent's state directory as declared in the Fabric job config for that agent.
- `launch`: start the agent command, `initialize`, `session/load` with the recorded id and the new `cwd`, and return `Spawned` with its pid, process group and start time.

Agents whose state directory is unknown to Fabric cannot be captured and the adapter says so at `detect` time.

### Claude Code and Codex adapters first

These two get dedicated adapters because the first gate is Claude Code and the second harness is Codex, and because both have known native resume paths that ACP wraps. Amended 2026-10-19: the surfaces below are the research's decisions, not options.

**Claude Code, through the CLI.**

- State lives under `~/.claude/projects/<slug>/`, where the slug is the workspace path with non-alphanumerics replaced by `-`, plus sidecars that one session can spread across several slugs (`<sid>/subagents/`, `tool-results/`, `file-history/<sid>/`, `tasks/<sid prefix>/`, `plans/`, `uploads/<sid>/`). `capture` enumerates `projects/*/<sid>*` and the sidecars by session id, never one slug. `restore` places them under the same keys because the root is identical on every node (ADR 0011).
- `launch` runs a foreground `claude --resume <session-id>` in the user's terminal, from the workspace root, and returns `Spawned`. It never uses `claude --bg`, whose own supervisor restarts a killed session and would defeat the fencing kill (ADR 0003), and it never sets `CLAUDE_CODE_RESUME_INTERRUPTED_TURN`, so a turn cut by a kill shows Claude the cut-off marker instead of re-running the tool. Headless checks, such as the adapter's own integration test asking the resumed session for its working directory, use `claude -p --resume <session-id>`; `-p` sessions are hidden from the picker and `--continue`, which is why the user-facing launch is interactive.
- Resume restores the conversation, model, agent and permission mode and nothing passed as a flag. The job record therefore holds the launch flags and `launch` passes them on every start: `--settings <job overlay file>`, `--mcp-config <job file>`, `--add-dir`, `--plugin-dir`, `--permission-mode`, `--fallback-model`, with `autoMemoryDirectory` and `plansDirectory` pinned in the overlay. Secrets in the overlay are references (`${VAR}`), never values, and the adapter refuses to write an overlay that holds a literal token.
- `stop` on a foreground session is the graceful exit the research names (H1, section 11.3). `detect` reports a session under the background supervisor (`claude agents --json`) as `Daemon`; `stop` for it is `claude stop <id>`, never a signal, because the supervisor restarts a process that "exited unexpectedly" and `claude respawn --all` restarts every supervised session after an update (design input, A34, D27). A `--bg` session is captured only after `stop` returned.
- Native tombstone: the adapter appends a `continued-in` record `{ type, sessionId, continuedInSessionId, timestamp }` to the departed transcript, which is the record the CLI itself writes when a conversation continues elsewhere. Whether `claude --resume` and the picker honour it is an open experiment (design input, A32); the record is written regardless because it costs one line and the undo truncates to the recorded byte length. Amended 2026-10-22 after review: the record is written when the departure commits, not by `capture` (Tombstones, below).
- Reuse of claude-handoff 0.3.0's exporter and redaction rules will be evaluated rather than rewritten (landscape section 8.1).

**Codex, through `codex exec resume` first.**

- State is the rollout lineage under `$CODEX_HOME/sessions/**/rollout-<ts>-<thread_id>[_<rollout_id>].jsonl[.zst]`, including every `history_base` predecessor of a paginated thread, plus parent and child threads of a multi-agent run. `capture` copies the lineage byte for byte; `restore` places it under `sessions/fabric/<thread_id>/` on the target, which the lookup accepts (H2, experiments E2 and E5). The SQLite files, `thread-writer-locks/`, `shell_snapshots/`, `environments.toml` and `auth.json` are never captured.
- `launch` runs the stable CLI: `codex exec resume <thread-id>` from the workspace root, with the sandbox, approval policy, model and effort from the job record passed as `-c` overrides on every run, because a cold resume on 0.155.1 downgraded `workspace-write` to `read-only` when they were not passed (H2, experiment E3). The app-server JSON-RPC surface is used only for interactive attach and only behind a per-version capability probe: `initialize`, then a check that every method the adapter needs is present and not marked experimental for this binary. `thread/resume { threadId, cwd, sandbox, config }` is stable in that base form; `path`, `history`, `historyMode`, `runtimeWorkspaceRoots`, `permissions` and `environments` are experimental and the adapter does not depend on them. The reason is churn: 79 commits to `app-server-protocol` in the 30 days to 2026-10-19, `thread/rollback` removed in 0.156.0, and "experimental, not supported for production workloads" in OpenAI's own docs (H2, section 10).
- `stop` and `capture` hold Codex's own writer lock for the whole copy: take `.coordination.lock`, then `try_lock` on `thread-writer-locks/<thread_id>.lock`, the pattern Codex uses for publication. Checking that the lock is free and then copying is a race the ChatGPT desktop app, automations and spawned child threads can lose for Fabric (design input, A8).
- Native tombstone: the adapter calls `thread/archive`, which moves the rollout to `archived_sessions/`, refuses while a live writer holds the lock, and removes the thread from `codex exec resume` and the picker; the undo calls `thread/unarchive`. Amended 2026-10-22 after review: the archive happens when the departure commits, not in `capture` (Tombstones, below). `capture` also lists every `automations/*/automation.toml` whose `target_thread_id` is the job's thread and refuses until they are disabled, because a scheduled automation is a writer on the departed machine (design input, section 4.8.1).

**Tombstones.** Added 2026-10-22 after review. Writing a tombstone in `capture` hid the thread from its own owner whenever the capture did not end in a departure: a standalone `fabric suspend` captures and publishes and the node still owns the job, and a move whose snapshot transfer fails stops before `MoveStarted`, and neither path has an abort to call `thread/unarchive`. The next resume on that node then named a thread `codex exec resume` no longer lists. `confirm_departure` is no place for it either, since it runs after every publish, the standalone suspend's included. So a tombstone is written only when the job leaves the node, and taken back whenever the node owns the job again:

- Written after the source's `MoveStarted` is durable (ADR 0003, step 3), on a push and on the holder's answer to a pull, and written again by the recovery that follows a crash there, while the decision is `MoveImported` or not yet known. Writing it is idempotent: the adapter records what it wrote (the transcript's length before the line, the archived thread id) beside the departure record of ADR 0015.
- Taken back when the node learns `MoveAborted` for that move, and before any launch on a node that owns the job, so a crash between the write and the abort, or an abort this node learns late, never leaves the owner a hidden thread. `capture` and a standalone suspend write nothing that a later resume on the same node must undo.
- Not built yet (ADR 0015, "Verified, and what still needs a live run"): neither adapter writes a tombstone today, so no path hides a thread; the rule above is where the code that writes one must hook in.

**Rules shared by both adapters.**

- No per-job config directory. `CLAUDE_CONFIG_DIR` and `CODEX_HOME` stay at the user's defaults on every node. Both harnesses key the login to the config directory (Codex derives its keyring entry from the `CODEX_HOME` path; Claude keeps `.credentials.json` or the Keychain item per config directory), so a per-job directory is a per-job login, which breaks the credential rule below (design input, D15; H6, section 2.4, item 6). Per-job settings are overlays passed as flags, never writes into `~/.claude.json` or `~/.codex/config.toml` while a harness may be running. Amended 2026-10-20 after review, and corrected the same day after a second review: the Claude adapter reads and writes `~/.claude.json` and `~/.claude` only, and in Claude 2.1.294 any value of `CLAUDE_CONFIG_DIR` moves both the config file (to `$CLAUDE_CONFIG_DIR/.claude.json`, even when the value names `~/.claude`) and the Keychain item (to `Claude Code-credentials-<hash of the directory>`), while an empty value moves the projects store to a relative path. `CLAUDE_SECURESTORAGE_CONFIG_DIR` renames the Keychain item too, and `CLAUDE_CODE_CUSTOM_OAUTH_URL` moves the config file to `.claude-custom-oauth.json` and the login with it. `ClaudeCode::check_env` therefore refuses a launch environment that sets any of the three, whatever the value (`ConfigMoved`, which says to unset it); `launch` and `ClaudeCode::preseed_trust`, which takes the launch environment for this reason, run it first, and the CLI runs it before it captures. Codex has the same gap: with `CODEX_HOME` naming another directory it writes the thread and looks for its login there while capture reads the adapter's store. `Codex::check_env`, run first by `launch`, refuses a launch environment under which Codex's home is not the store (`CodexHomeMismatch`); because Codex canonicalizes a set value and keys its keyring entry by the canonical path, and treats an empty value as unset, a value that names the store under another spelling is accepted.
- Trust on the target. Claude blocks an interactive session on a new path with a trust dialog, and `--bg` exits with "Workspace not trusted". Before `launch`, the Claude adapter sets `projects["<root>"].hasTrustDialogAccepted = true` in `~/.claude.json` by read, modify, temp, rename, and only while no `claude` process runs on the node; if one runs, it refuses with `ClaudeRunning` and names the process, because Claude rewrites that file itself. Amended 2026-10-20 (gate finding F1): the refusal blocked every run on the first gate, because the owner keeps Claude Code open all day, and it fired even when nothing needed writing. `ClaudeCode::preseed_trust` now reads `~/.claude.json` first, read only, and returns a `TrustOutcome`. When Claude already trusts the workspace it returns `AlreadyTrusted { key }` and neither writes nor looks at processes. Corrected 2026-10-20 after a second review: Claude 2.1.294 has two trust checks, and only the stricter one counts as trusted. The dialog check walks from the working directory up through its ancestors to the first `projects` entry with the key set, stopping at the repository root inside a git repository (read from the 2.1.294 bundle; a new folder under the trusted home opened with no dialog, measured 2026-10-20). The project settings check reads one key with no walk: the main checkout of the git repository that holds the working directory, found for a linked worktree through its `.git` file, `commondir` and `gitdir`, or the working directory outside a repository, and the value must be a literal `true`. Only that check turns on the workspace's `permissions.allow` rules, `.mcp.json` servers, additional directories and project hooks; with a trusted ancestor alone, a subdirectory key in a repository, or the worktree's own path as the key, `claude -p` printed that it ignored the workspace's allow rule and named the key it wanted (reproduced with a temporary home, 2026-10-20). Fabric therefore computes that key (`trust::project_key`), returns `AlreadyTrusted { key }` only when it is a literal `true`, and writes that key. When it does not write but an ancestor the dialog walk reaches is trusted, it returns `Inherited { by, reason }`, which the caller warns about because Claude runs without the project settings. Claude spells the keys as the NFC form of the real path; a workspace whose physical path is not NFC (a name stored decomposed on APFS) is refused before trust is read, because its root cannot be an `AbsPath` (ADR 0004), so Fabric never writes a key Claude would not look up. When the key is not `true` and no `claude` runs, it writes the key (`Written { key }`) under an exclusive lock on `~/.fabric/harness/locks/claude-config.lock`, so two Fabric processes never lose each other's key (amended 2026-10-21 after review), unless `~/.claude.json` is a symlink, as a dotfile manager makes it: then the rename would turn the link into a plain file, so it writes nothing and returns `LeftToClaude { reason: ConfigIsSymlink }` (amended 2026-10-20 after review). A missing `~/.claude.json` is not created and is not an error either (`LeftToClaude { reason: NoConfig }`): a node logged in with `ANTHROPIC_API_KEY` alone may never have run Claude, and Claude creates the file and asks. When one runs, it writes nothing and returns `LeftToClaude { reason: ClaudeRunning { pids } }`, with a pid list that cannot be empty, not an error: the caller warns and launches, an interactive Claude shows its own trust dialog, and a headless `claude -p`, which never shows one, runs without the workspace's project settings. Each of these is `Inherited { by, reason }` instead when an ancestor the dialog walk reaches is trusted. The file read and written is `~/.claude/.config.json` instead of `~/.claude.json` when it exists, because Claude 2.1.294 prefers that legacy file (read from its bundle and seen with a temporary home, 2026-10-20). Codex trust is an exact key on the path, so the adapter passes `-c projects."<root>".trust_level=trusted` on every run instead of editing `config.toml`.
- Versions are recorded in the job record on every suspend (`claude --version`, `codex --version`) and compared by `fabric doctor` (ADR 0008). Claude 2.1.300 fixed a lost first transcript entry after a crash-cut resume, which is the kill -9 gate path, so the floor for the gate is 2.1.300 on both nodes; neither Mac meets it today (Pro 2.1.294, Air 2.1.199; `step1/preflight-2026-10-19.md`), and auto-update is turned off for the duration of a measured run (`DISABLE_AUTOUPDATER=1`, pinned Homebrew Codex).
- Secondary harnesses come later and in this order: OpenCode (export and import JSON, the cheapest carry), then Pi (one JSONL under a directory Fabric may own). Copilot, Cursor and Amp wait for a read of their terms (design input, D17).

Each adapter is a module in `fabric-harness` behind a cargo feature. The core compiles with no adapter enabled.

### Credentials and terms

Added 2026-10-19.

- Fabric never carries, copies or proxies a credential: not `.credentials.json`, not a Keychain item, not `auth.json`, not an OAuth token in an MCP configuration. Each node signs in once, at its own console, through the vendor's own flow; a login over SSH may fail to reach the Keychain and fall back to a plaintext file, so the first login on the Air is done at the Air (design input, section 5.4). `fabric doctor` reports login presence as yes or no and never the account.
- That rule is Fabric policy, stricter than one vendor requires. Anthropic forbids developers from collecting, storing or intermediating Claude.ai credentials or session tokens; OpenAI's own documentation describes copying `auth.json` to a headless machine. Fabric keeps the strict rule on both because two copies of one login on two machines is the split-brain the lease exists to prevent.
- Running the unmodified vendor CLI under the user's own login on the user's own machines is the use both vendors allow: Anthropic's compliance page covers "ordinary use of Claude Code" and signing in to the unmodified binary with one's own subscription, and documents `-p` and `setup-token` for scripts; OpenAI allows local and open-source use of the app-server and has never allowed it for commercial or hosted services. An adapter that runs a harness for other people is not covered by either reading and is out of scope (design input, D20; H1, section 10; H2, section 9). Fabric does not modify either binary, does not remove an auth method, and does not use either product's name in its own.
- Code the adapters may draw on: claude-handoff, session-roam and session-migrate are MIT; openai/codex is Apache-2.0; `coder/agentapi` is MIT. cmux is GPL and is studied, never copied (design input, D21).

### Harness state is opaque to the core

The core sees `harness_state` as a list of relative paths and chunk ids. The only thing the core does with it is hash, store, transfer and hand it back to the adapter. The core never redacts, never parses JSONL, never rewrites paths. Redaction is therefore part of the `Harness` contract, not an option: `capture` returns a `RedactionReport` per rule applied, and the suspend output prints the counts next to the excluded workspace paths (ADR 0004).

For the Claude Code adapter the contract is concrete, because the research shows what the state carries (H1, sections on the config directory and on identity):

- Never included: `.credentials.json`, anything derived from the Keychain, `~/.claude.json` as a whole (it holds `oauthAccount`, `machineID`, `remoteControlMachineId`, `userID`), `sessions/`, `session-env/`, `shell-snapshots/`, `jobs/`, `daemon/`, `backups/`, `cache/`, `telemetry/`, `stats-cache.json`. Each node signs in once through Anthropic's own flow; carrying credentials would also breach the terms the research cites.
- Redacted in the transcript and sidecars, following claude-handoff 0.3.0's rules: secret patterns, `.env` values that appear in tool results, the account email and the organization UUID in `session_context` and `credential_org` attachments. Corrected 2026-10-20: the email and the organization UUID are not redacted yet; ADR 0015, "Redaction as built", says what is and why.
- A secret inside a signed `thinking` block cannot be edited without breaking the block (next section). The adapter then drops that whole block, which the API accepts, and counts it in the report.

### State outside the root is protected like the root

The workspace marker (ADR 0004) keeps a restore from writing over unpublished work in the root. Harness state lives outside the root, so the adapter must give the same guarantee itself. Before `restore` overwrites a file it owns on this node, it compares the bytes on disk with the incoming bytes: equal, or a byte prefix of the incoming file, is allowed, because nothing on disk is lost; anything else is `HarnessStateDiverged { path }` and nothing is written. This is the rule cmux uses for Claude transcripts (research H1, section 9) and it fits because transcripts only grow. Corrected 2026-10-20: not every file grows; ADR 0015 adds the rule for files a harness rewrites in place. The case it catches is the old holder of a fenced job: its transcript continued past the fork while the job's transcript continued elsewhere. The way out is `fabric orphan export`, which captures the divergent state into an orphan snapshot (ADR 0003); after that the files on disk may be replaced. Amended 2026-10-22 after review: comparing only the paths the incoming state holds misses a file the fenced holder created that the incoming state lacks, such as a new memory file, sidecar or rollout, which the resumed harness would then read beside the incoming history. Restore therefore also lists what the adapter would capture for the session on this node and refuses any such file the incoming state does not place, unless it is a rewritable file this node left untouched since the job left, which the job dropped and which is removed (ADR 0015, the manifest and what restore may do).

### Path rewrites: none by default, never inside a signature

`restore(state, from_root, to_root)` receives `SnapshotManifest.root` as `from_root` (ADR 0004); `Captured.absolute_roots` is what the adapter reports at capture and the core checks it against that field. With `from_root == to_root` it performs no rewrite at all, and in v0 that is the only case the Claude Code adapter accepts (ADR 0011). The reason is a fact about the state, not caution: Claude Code thinking blocks carry an encrypted `signature`, and a modified block is rejected with a 400 on the next tool turn (research H1, item 2). A blanket rewrite of the transcript breaks the resumed session at its first tool call, which is exactly the first gate.

When roots differ, which no v0 path allows for Claude Code, the adapter rewrites only the project directory key, `cwd` fields and sidecar references, following claude-handoff's placeholder rules at path-component boundaries, and never a `thinking` block or any field under a signature. Since 2.1.300 the transcript also records the system prompt of the first request, environment block included, and reuses it until compaction; a rewrite under different roots must either rewrite that record or pass `--system-prompt-snapshot off` on the first resume (design input, A2). Under the same root the stale fields are host-level only. The property test for this is stated now so that it exists before the code: for arbitrary roots, a rewritten transcript leaves every signed block byte-identical.

### Cross-harness resume is an experiment, not a promise

`fabric resume <job> --harness codex` on a job captured under Claude Code cannot load Claude's native state into Codex. What it can do is produce a neutral brief (goal, recent decisions from the ledger, `git log` and `git status` of the restored workspace, the last user turn if the source adapter exposes it) and start the new harness with that brief as its first prompt. This is the same text-handoff shape T3 Code uses and it loses tool state and approvals. It is listed as a later experiment. Fabric does not claim it works until a measured test says how much is lost.

## Alternatives considered

1. **Drive agents through their SDKs** (Claude Agent SDK, Codex app-server as a hosted service). Both carry terms that restrict third-party hosting and login use (landscape section 8.1). Fabric runs the user's own CLI under the user's own login on the user's own machines, which is the path the research reads as allowed. SDK coupling is also the fastest way to a core release per vendor release. Rejected for the core; an adapter may use an SDK internally if its terms allow.
2. **`coder/agentapi` as the only path.** HTTP over several CLIs, MIT. It does not capture or restore state, which is the part Fabric needs. Could be a launch mechanism inside an adapter. Not the trait.
3. **A Fabric-defined session format that every agent must export to.** Nobody would implement it. Rejected. The opaque state directory plus per-adapter knowledge is the pragmatic version.
4. **Transcript-only moves** (claude-handoff, session-roam). Covers Claude only and omits the workspace. Used as a reference and possibly a library inside the Claude adapter.

## Consequences

- Adding a harness is one module and one feature flag. No core change.
- A vendor changing its state layout breaks one adapter's tests, not the system.
- `detect` returning `None` is a normal answer and the CLI explains it ("no Claude Code session found for this workspace"). Corrected 2026-10-20: `detect` only says whether the binary is installed; finding a session is `latest_session` (ADR 0015).
- Adapter tests are integration tests against the real CLI when installed, skipped with a clear message when it is not. Corrected 2026-10-20: every adapter test runs against fixtures and fake binaries; the real CLIs are exercised on the two-Mac gate (ADR 0015). Property tests cover redaction over arbitrary JSON, including the byte-identical signed block property above; path rewriting has none because no rewrite exists in this phase (ADR 0011).

## Open questions

- Does `session/load` in `claude-agent-acp` restore the same context as native `claude --resume`? Test both on the gate.
- Do the native tombstones hold? After a scripted move, on the source run `claude --resume <sid>`, the Ctrl+A picker, `codex resume <id>` and `codex exec resume <id>`; pass is a refusal or a visible fork, fail is a silent resume (design input, A32, A33). If both fail, the remaining guard is moving the native files out of the harness store on depart, which makes abort harder, and ADR 0003's open question about moving the departed copy becomes a decision.
- Pending approvals: drain or cancel at capture, re-ask on launch. The research recommends not moving them (t3code note, section 2). Confirm with the first real suspend of a job mid-approval.
- Subagent transcripts and memory files outside the project directory: adapter decides what is part of "state". Start with what claude-handoff includes.
