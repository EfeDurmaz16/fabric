# ADR 0007: Environment spec

Status: accepted, 2026-10-19

Amended 2026-10-19 after step 1 research. Step 1 of Materialize now reads the per-cache carry key of ADR 0012 instead of the `{ os, arch }` pair alone. The exact strings `fabric doctor` compares (ADR 0008) live in the carry key, not in `tools`, which holds the workspace's own pins as written (corrected in place by the `feat/env` amendment). Nothing else changed.

Amended 2026-10-19 while writing `fabric-core` (PR `feat/core`): `SetupStep.cwd` is `Option<RelPath>`, where `None` is the workspace root, because a `RelPath` cannot name the root itself (ADR 0004 forbids empty and `.` components). The edited-spec record is `EnvSpecChanged` (ADR 0002), not a free-text `Note`.

Amended 2026-10-19 after the adversarial review of PR `feat/core`: a setup step is `{ program, args, cwd, when }` rather than `{ argv, cwd, when }`, so the shape matches `HarnessKind::Acp` (ADR 0006). The second review found that this alone did not remove the empty command: `program` was a bare string and `""`, `/tmp/x`, `../bin/x` and `-rf` all decoded. `program` is now `ProgramName`, a parsed type that is non-empty and holds no slash, no NUL and no leading `-`, checked inside `Deserialize`, so "looked up on `PATH`" is true by type. The format version is the first varint of the spec's bytes, not a field of the struct (ADR 0002, review amendment 5).

Amended 2026-10-19 after the second adversarial review of PR `feat/core`: `program` is a `ProgramName` (amendment above, corrected in place), `env_var_names` holds `EnvVarName` values that cannot carry a `=`, and `tools`, `env_var_names` and `cache_paths` are strictly sorted so that one content has one `EnvSpecId`; a spec that breaks either rule is refused on encode and on decode.

Amended 2026-10-19 and 2026-10-20 while writing `fabric-env` (PR `feat/env`) and after its five reviews. Detection and materialize are corrected in place, with the reason next to each rule. What changed: pins are kept as their files write them and never compared; the user's edits live in `.fabric/env.toml`, not in an edited copy of the spec; a job's secret patterns are recorded in its spec and only grow; tool names, pins, setup arguments and secret patterns are parsed types checked on decode; detection reads regular files only, drops a detected pin that breaks the pin rules and refuses Yarn Plug'n'Play; every cache has an ecosystem, an origin and a completion proof, and every step is tied to the caches it fills, in the detection report; a cache a step fills is proven by Fabric's sentinel and never by an installer's own marker; one installer per tree is guarded by a lock in node state; and every resume detects again before it plans.

Amended 2026-10-22 after review: the spec travels, as this ADR says it does. Until then no node stored or sent a spec's bytes, snapshots carried `env_spec: None`, and the patterns a job recorded lived only in the capturing node's `jobs/<job-id>/secret-patterns` (ADR 0016), so after a move the target lost every pattern the override file no longer listed and its next capture carried what the source had denied. Capture now stores the spec's canonical bytes as one object and the snapshot names it in `env_spec`. An `EnvSpecId` and a `ChunkId` are both blake3 of the same bytes, so the id is the object's: `Store::data_chunks` lists it, publish refuses a manifest whose spec object is missing, gc keeps it while the snapshot is kept, and a peer that fetches the snapshot fetches the spec with the same `WantChunks`. The patterns `detect` takes as recorded are those of this node's file joined with those of the spec the job's latest snapshot names, so a pattern recorded on any node stays in force on every node the job reaches. Writing `EnvSpecChanged` to the ledger is still not built.

Amended 2026-10-24 for issue #25: `TreeLock::acquire` retries a busy lock for one second before it refuses. A child that any thread forks shares the lock's open file until it execs, so a lock released in that instant looked held, and on macOS CI the second of two suspends in a row refused with `SetupRunning`. The lock stays an `flock`; "One installer per tree" says why a POSIX record lock was rejected.

## Context

The job's workspace arrives with its caches when the platform matches (ADR 0004). When it does not, or when a cache was excluded, the node must be able to make itself ready without the user typing anything. The standard for describing environments is `devcontainer.json` (about 1.69M monthly npm downloads of `@devcontainers/cli` per the landscape, section 7). But a devcontainer is a container recipe, and v0 runs harnesses directly on two Macs with no container.

Also: environments contain secrets, and secrets must not travel in snapshots (ADR 0004 policy).

## Decision

### `EnvSpec` v0

```text
EnvSpec {                        the bytes start with the format version as a varint; it is not a field
  tools:         [Tool],         detected or declared pins, informational, printed beside measured versions, never compared; strictly sorted by name
  setup:         [SetupStep],    commands that make the workspace runnable, in the order they run
  env_var_names: [EnvVarName],   names only, never values; `[A-Za-z_][A-Za-z0-9_]*`, strictly sorted
  cache_paths:   [RelPath],      what counts as a cache for snapshot policy and for "is it warm"; strictly sorted
  secret_patterns: [SecretPattern], patterns the job added to the built-in secret list; only grows; ASCII lowercase; strictly sorted
}
Tool      { name: ToolName, version: ToolVersion, source: Detected | Declared }   version is the pin as its file wrote it, never parsed into parts; both are 1 to 64 printable ASCII characters (no space in a name), not credential-shaped, checked on decode
SetupStep { program: ProgramName, args: [SetupArg], cwd: Option<RelPath>, when: CachesMissing | Always }   cwd None is the root; ProgramName is a bare name with no control character, never a path or an option; a SetupArg has no control character and is not credential-shaped, checked on decode
```

`program` is looked up on `PATH` and run with `args` directly, never through a shell. A spec travels with the job and a peer can send one, so there is no string for quoting bugs or a hostile `packageManager` field to hide in. Every part a peer can fill is a parsed type checked inside `Deserialize`: a tool name, pin or setup argument that holds a token or a terminal escape would otherwise reach other nodes and the prompt below. Before a node runs the steps of a spec whose id differs from the one it last ran for that job, or of the same spec over other install inputs (step 4), the command prints the steps and asks, unless it was given `--yes`.

`EnvSpecId` is the blake3 of the postcard bytes. A job references an `EnvSpec` by id; editing produces a new id and an `EnvSpecChanged` record in the ledger. The id is only an identity if the same content has one byte form, so `tools`, `env_var_names`, `cache_paths` and `secret_patterns` are strictly sorted by their key and a spec that is not, from a peer or from a caller, is refused with `EnvSpecError::OutOfOrder { list, index }`; `setup` keeps the order it runs in. A secret pattern is stored in ASCII lowercase, because matching ignores ASCII case: `*.DB` and `*.db` are one rule and one value, and a decoded pattern with a capital is refused. An environment variable name is a parsed `EnvVarName` that cannot hold `=`, so a value cannot travel inside a name (second review of PR `feat/core`, 2026-10-19).

### Detection

Detection runs at `fabric job init`, at `fabric suspend` when the job has no spec, and on every resume before materialize (below). It reads a fixed list of regular files at the workspace root, follows no link, never reads a file the secret policy denies or an environment variable, and runs no program, so the same files give the same spec on every node. A symbolic link in its list, in any component of the path, is refused with the file named, and the opened handle must be the file the link check saw: `.nvmrc -> .env` would read a secret into the spec, and `.nvmrc -> ../../.nvmrc` would give two nodes two specs from one workspace. A file it only checks for, such as a lockfile, `Cargo.toml` or `uv.lock`, is refused the same way when it is not a regular file, or a link other than one to a regular file inside the workspace that the secret policy does not deny: the step it selects reads it, so `package-lock.json -> ../lock.json` would have `npm ci` read a file outside the workspace that can differ from node to node (review of PR `feat/env`, 2026-10-22). A link inside the workspace, as Django's `requirements.txt -> requirements/base.txt`, travels as a link and resolves the same on every node, so it counts as the file it names, and its install inputs are that file's bytes (review of PR `feat/daemon-cli`, 2026-10-22).

Detection also hashes, without keeping them, the files each ecosystem's steps read at the root: `package.json` with the chosen manager's lockfiles and configuration (`.pnpmfile.cjs` and `pnpm-workspace.yaml` for pnpm, `.yarnrc` or `.yarnrc.yml` for Yarn, `bunfig.toml` for Bun; `.npmrc` is a secret and never read), `Cargo.toml` and `Cargo.lock`, `pyproject.toml` and `uv.lock` or `requirements.txt`, and `go.mod` and `go.sum`. The report keeps one digest per cache: its ecosystem's files, or every hashed file for an `other` cache, which nothing says how to make. The spec holds the commands, not these files, so this digest, not the `EnvSpecId`, is what changes when a lockfile does (step 3 of Materialize).

- `package.json` plus a lockfile: the manager is `package_manager` in `.fabric/env.toml`, else `packageManager` in `package.json`, else the only manager with a lockfile (`pnpm-lock.yaml`, `package-lock.json` or `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock` or `bun.lockb`). Setup is its frozen install with `when: CachesMissing`: `pnpm install --frozen-lockfile`, `npm ci`, `yarn install --frozen-lockfile` for Yarn 1, `yarn install --immutable` for Yarn 2 and later (from `packageManager`, else `.yarnrc.yml`), `bun install --frozen-lockfile`. Cache path `node_modules`. `.pnpm-store` is not a cache path: ADR 0012 never carries pnpm store files, and with the usual global store the path would be missing on every resume. Two lockfiles with nothing to choose between them, or a chosen manager whose lockfile is absent while another's is present, stop detection with a message that names the fix. No lockfile: no step and no cache path, because nothing can rebuild that `node_modules`, so it travels as precious files (ADR 0004).
- Yarn 2 and later must set `nodeLinker: node-modules` in `.yarnrc.yml`; Plug'n'Play, the default, is refused. It writes no `node_modules`, so the detected cache would be missing on every resume, and its `.yarn/unplugged` holds native builds for one Node ABI with no carry key. Detection reads the one key `nodeLinker`, line by line, and never quotes its value. Supporting Plug'n'Play needs a cache shape for `.pnp.cjs`, `.yarn/install-state.gz` and `.yarn/unplugged`; it waits for a job that needs it.
- `Cargo.toml`: setup `cargo fetch`, plus `--locked` when `Cargo.lock` exists, so a resume never rewrites the lockfile; cache path `target`.
- `uv.lock`: setup `uv sync --frozen`. Else `requirements.txt`: setup `uv venv --allow-existing .venv`, then `uv pip install --python .venv -r requirements.txt`, not `pip install -r`, which writes into whichever Python is first on `PATH`. Both name `.venv`, because without `--python` uv installs into an activated `VIRTUAL_ENV` or `CONDA_PREFIX` the resume shell inherited before it looks for the workspace's `.venv`. Cache path `.venv` for both. A `pyproject.toml` without `uv.lock` gives nothing, because a sync would write a new lockfile.
- `go.mod`: setup `go mod download`; no cache path in the workspace.
- Tool pins, first wins per tool: `[tools]` in `.fabric/env.toml` (`Declared`), `mise.toml`, `.tool-versions` (`nodejs` read as `node`, `golang` as `go`), `rust-toolchain.toml`, `.node-version`, `.nvmrc`, `.python-version`, the `go` directive of `go.mod`, then `packageManager` and `engines.node` of `package.json`. The detection report keeps every pin with its file, so a disagreement is visible. A pin is kept as its file wrote it (`22`, `1.97.1`, `>=18`); the strings a tool reports about itself are measured by `fabric doctor` and stored in the carry key (ADR 0008, ADR 0012). Every tool name and pin must be at most 64 printable ASCII characters and not shaped like a credential, since pins travel in the spec. A detected pin that breaks this is dropped with a warning that names the file and the place in it (a key, a `[tools]` entry or a line) and never the text: pins are informational, so one that nothing reads must not stop a resume. A pin in `[tools]` of the override file is refused instead, because the user wrote it on purpose.
- `.devcontainer/devcontainer.json` or `.devcontainer.json`: recorded in the report, not interpreted.
- Env var names: only those `.fabric/env.toml` declares. Scanning `.env.example` and source code for names is not built; a scan that guesses would put names in the spec that the user never chose.

The detection report also gives each cache path its class (ADR 0004), its origin (`Detected` or `Declared`), its ecosystem, which picks the carry key the store measures (ADR 0012), and how materialize proves it whole (step 2 below). A declared cache without `ecosystem` takes the single detected ecosystem, `other` when none was detected, and detection stops when two were (ADR 0012, 2026-10-20 amendment). The report also records which caches each setup step fills. It lives beside the spec rather than in it: every node rebuilds it from the same files, so linking a step to its cache needs no spec format change. A report cannot be stored or sent, because it holds the node's resolved workspace root.

### The override file

`.fabric/env.toml` is what the user declares. The spec is rebuilt from the files and the override file, so "edit the spec" and "detect again" cannot disagree. A declared tool pin replaces a detected one. `package_manager` decides between lockfiles. Any `[[setup]]` entry replaces every detected step, and `setup = []` declares that nothing runs. `[[cache]]` adds a cache path with its class and, optionally, the ecosystem that makes it (`node`, `rust`, `python`, `other`); a path detection also found keeps its ecosystem, so a declared class cannot send a `node_modules` to a node with another Node major, and a declared `ecosystem` that differs from it is refused. A cache path under `.fabric`, or one that lies inside or contains another declared or detected cache, is refused: a cache is dropped on a carry mismatch, and a directory that holds the user's work must not become one by accident. A declared cache keeps the full secret list; only the caches detection found get the narrowed one (ADR 0004), since a declared path can be a mistake that holds the user's own `.env.local` (`.git` cannot be a `RelPath` at all). `env` lists variable names. `secret_patterns` widens the secret list. Unknown keys are refused.

The file names things and never carries a value. A `NAME=value` in `env` is refused. A setup argument shaped like a credential (a GitHub, GitLab, npm, Slack, Hugging Face or PyPI token, an `OpenAI`, Anthropic, Stripe or Google API key, an AWS key id, a PEM header, a URL with a password) is refused, because the spec travels to other nodes. No error quotes a value from the file; errors carry key paths, indexes and line numbers, and quote an unknown key's name only when it is at most 64 printable characters and not credential-shaped. Detection skips any file in its list that the job's secret patterns deny, so `secret_patterns = ["mise.toml"]` keeps that file's pins out of the spec, and counts a denied file it only checks for, such as a lockfile or `Cargo.toml`, as absent: capture leaves it behind, so the next node detects without it and the two specs agree. A pattern shaped like a credential is refused by `SecretPattern::parse` and on decode, as a setup argument is, because patterns travel in the spec. A pattern that would deny the override file itself, such as `*.toml`, `env.toml` or `.fabric`, is refused by `SecretPattern::parse` and on decode: it would drop every override, declared steps and variable names included, from the next detection on.

### Materialize on restore, only when needed

After restore, `fabric resume` holds the tree's lock (below) and `fabric-env` checks, in order:

1. Restore has already written each carried cache whose platform and carry key match this node and which is not partial, and skipped the rest (ADR 0012). A cache the secret policy punched a hole in, or one measured under a different pnpm store path or rustc, is therefore absent on disk, however full it was on the source.
2. Resume detects again: `detect(root, &recorded.secret_patterns)` over the restored tree, where `recorded` is the spec the ledger last named for the job. `plan` needs a detection report, and a report is node-local, so every resume builds its own. When the new `EnvSpecId` differs from the recorded one, because the override file changed or detection found other steps, the owner appends `EnvSpecChanged` at its epoch (ADR 0002) before any step runs, and the prompt before a spec this node has not run applies. A lockfile changed with the same manager leaves the id as it was; step 3 catches it, and the prompt asks again because it keys on the install inputs too.
3. For each cache path in the report: is it a non-empty directory holding proof that whatever filled it finished? For a cache a setup step fills, the detected `node_modules` included, the proof is `.fabric-installed`, a sentinel materialize removes before the first step that fills the cache starts and writes after the last one exits 0. An installer's own file is not proof. npm writes `node_modules/.package-lock.json`, pnpm `.modules.yaml` and Yarn 1 `.yarn-integrity` before the root package's `preinstall`, `install`, `postinstall` and `prepare` scripts run, so a script that fails, or a Ctrl-C during it, leaves the marker over a tree that is not whole. `uv venv` writes `pyvenv.cfg` before any package, and Bun writes no marker at all. The cost is that a `node_modules` installed outside materialize, such as by the user on the source node, installs once more on the first resume. A cache no step fills, such as a detected `target` that a build makes, needs only content. An install that fails or is killed halfway leaves no proof, so the next resume fills the cache again; a carried cache keeps the sentinel its source wrote.
   - The sentinel holds the digest of the cache's input files (Detection, above) and proves the cache only while they are unchanged. A sentinel written for other inputs, such as one carried from a node where the lockfile had not yet changed, or one left before a pull rewrote `package.json`, makes the cache stale, and the steps that fill it run again. Before this, a lockfile change left both the spec and the sentinel as they were, and resume launched over packages the lockfile no longer named (review of PR `feat/env`, 2026-10-22). Materialize writes the sentinel over whatever a step left at its name, so it always names the inputs of the run that wrote it.
   - The sentinel is a file inside the cache, so it is also written into a declared build output such as `dist`, and a `npm publish` or deploy of that directory ships it. Keeping proofs in node state instead would lose them on every carry and rebuild each declared cache after a move; the in-tree file is the smaller cost, and the name says what wrote it.
   - Power loss is out of scope for this proof. Nothing is synced, and after a power loss or kernel panic the filesystem may keep the sentinel and lose installer files written before it. Syncing a whole `node_modules` costs seconds on every install, and the first gate's failure case is `kill -9`, where the kernel keeps every write.
4. Run each `setup` step with `when: CachesMissing` whose caches are not whole, in order, in the workspace. A detected install fills its own cache and runs only when that cache is not whole, so a missing `target` never runs `npm ci` over a healthy carried `node_modules`. `cargo fetch` runs when `target` is not whole, since a build makes `target` from what it fetches. A step the user declared counts as filling every cache but a detected `target`, and runs when one of those is not whole. `go mod download` fills only this node's module cache, which lies outside the workspace, is never carried, and which nothing in the workspace proves warm, so it runs on every resume; a healthy carried `node_modules` beside it says nothing about this node's modules (review of PR `feat/env`, 2026-10-22). A declared step that fills no cache runs when any cache is not whole or the report has none: "is any cache missing" is vacuously false over an empty list, nothing in an empty list proves the workspace warm, and a user who wants such steps skipped declares the path they rebuild as a `[[cache]]`. Steps run with the node's environment plus the job's env var names resolved from the node's own secret source (v0: the user's shell environment on that node). A detected `uv` step runs without `UV_PROJECT_ENVIRONMENT`, `UV_PROJECT` and `UV_WORKING_DIR`: inherited from the resume shell, each makes uv fill another environment or read another project than the workspace's, so the step succeeds, changes something outside the workspace and leaves `.venv` missing for every later resume. The detection report names the variables per step, as it names the caches; a declared step keeps the environment it inherits. The steps run in the `fabric resume` process, not in the daemon, which is why the user's shell environment is available (ADR 0004, one writer). Before any step runs, every planned program must be on `PATH` and every declared variable must be set, or nothing runs and the error lists what is missing. The variables are checked when no step runs too: the job needs them, so a warm node refuses where a cold node would. A cache a planned step fills that is a link, lies under one, or is not a directory also stops the plan before anything runs: the installer would follow the link, as `uv venv --allow-existing` does with `.venv -> ~/venvs/other`, and fill a directory outside the workspace. `PATH` entries inside the workspace are skipped, so a restored workspace cannot replace the installer binary. It can still run code through the installer: lifecycle scripts, `.pnpmfile.cjs`, source builds and declared steps all come with the snapshot, so a restored workspace is trusted as far as the peer that signed its snapshot (ADR 0004 threat model), and the prompt before a spec this node has not run (above) is where the user approves that code. The prompt keys on the spec's id together with the input digests the detection report keeps per cache (`Detection::inputs_digest`): the files each cache's steps read, a manager's own configuration included. The pair is recorded in `jobs/<job-id>/env-spec-ran` once approved, so an agent's edit of `package.json` scripts, a lockfile or `.pnpmfile.cjs` asks again before the install that reads it runs, as an edit of `.fabric/env.toml` does (review of PR `feat/daemon-cli`, 2026-10-22). The steps run more than those files: a script a declared step names, a file a lifecycle script runs, a workspace member's `package.json`, the Yarn release `yarnPath` names, a build backend. No digest covers them, so a node that restores a snapshot another node captured removes its record, and the next launch that runs a step there asks again, whatever the agent edited on the other node (second review of the same day). On the node where the agent ran, an edit of such a file still runs at the next launch that runs a step without a new prompt; see the open questions. Each line a step prints goes to `tracing` under the target `fabric_env::setup`; computing the plan is the dry run and changes nothing.
5. `Always` steps run on every resume.
6. The spec's pins are informational. `fabric doctor` prints each pin beside the string it measured for that tool (`node --version`, `rustc -vV`), so the user sees `22` next to `v26.1.0`, and compares nothing: ADR 0008 compares exact strings only, and a pin such as `>=18` or `v20` is not one, so an equality test would warn on every resume. The measured strings that do decide anything are in the carry key (ADR 0012). Nothing in materialize reads the pins.

If all caches are present, nothing runs and resume is fast. This is the common case for the two-Mac gate.

### One installer per tree

A step is not tied to the `fabric resume` process, so after a `kill -9` of resume during `pnpm install`, the first gate's own case, the installer keeps running. A second resume must neither restore over it nor start a second installer, or an `npm ci` that deletes the tree first. The guard is `TreeLock`, a `flock` on `<locks>/<blake3 of the resolved root>.lock` in the node's own Fabric state, never a file in the workspace: `git clean -xfd`, the agent or a restore in place can delete anything in the tree, and a lock they can unlink guards nothing. A lock directory inside the workspace is refused, and so is a lock file that is a link or not a regular file, checked before the open and by device and inode after it: a link would lock whatever it names, such as a workspace file a restore replaces with a new inode. The CLI takes the lock before restore writes the tree and holds it through `plan` and `execute`, which take it by reference, so neither runs without it.

`execute` passes the lock's open file to every step twice: as its standard input, an empty file that reads as end of input, and under a descriptor number of 3 or above without close-on-exec, which resume closes in itself as soon as the step has started. A step that replaces its input, as `sh -c 'exec </dev/null; ...'` does, keeps the second; with the input alone it dropped its only copy, and a resume killed then let the next one start a second installer (review of PR `feat/env`, 2026-10-22). The copy is made with `rustix`, which the workspace already builds, so no crate needs `unsafe`. The lock belongs to the open file, so the installer and every process that inherits either descriptor hold it after resume dies, and it ends when the last of them exits; no pid file can go stale. `TreeLock::acquire` refuses with `TreeBusy` while it is held, and names the lock file. A process a step leaves behind with either descriptor still open holds the lock too, so resumes refuse until it exits. A test kills a resume with SIGKILL during a step, deletes `.fabric` and writes it again as a restore would, and shows the next resume refuses until the orphan exits.

Holding the lock through the open file has a cost. A child that any thread of the holding process forks gets a copy of every descriptor, the lock's included, and keeps it until it execs, when close-on-exec drops it. If the holder releases in that instant, the child still holds the lock, and an acquire refuses although nothing runs in the tree. The node starts programs such as `ps` and `git` from its worker threads while it holds tree locks, and the test suite starts them from many threads at once, so on macOS CI the second of two suspends in a row refused with `SetupRunning` (issue #25). `TreeLock::acquire` therefore retries a busy lock every 20 ms for one second before it refuses, as `Store::open` does for the same reason (ADR 0014). A child keeps its copy only until its exec, far less than a second; a step, or a process one left behind, holds the lock for as long as it runs, so a refusal still means what it meant and comes a second later. The node takes the lock on a blocking thread, so that second never holds up its runtime. A test hands the lock's open file to a child that keeps it for 200 ms, releases the lock, and takes it again.

A POSIX record lock (`fcntl` with `F_SETLK`) was rejected. It belongs to a process, not to an open file, so a forked child does not get it, which removes the race; for the same reason a step does not get it either, and a resume killed during `pnpm install` would leave the running installer's tree unlocked, the first gate's own failure. A record lock also does not exclude a second acquire in the same process, and closing any descriptor of the file drops it, so the node would need a table of the locks it holds. Unlocking before the close (`LOCK_UN`) would end the lock for every process that shares the open file, a process a step left behind included, which the paragraph above relies on.

### Secrets

Names travel, values do not. Each node resolves values locally. v0 reads the shell environment. Later sources (1Password Environments, Tailscale Aperture, a per-node secrets file) are each a small resolver behind one trait; the research lists both services as integrate-not-rebuild (landscape section 8.1).

A job's own secret patterns are kept in its spec, in `secret_patterns`. The override file is a working-tree file the agent can rewrite, so a list kept only there would shrink when a line is deleted, and the next suspend would carry what it had denied. `detect` takes the patterns the job's last spec recorded and keeps the union of those and the file's; a pattern the file dropped stays in force and a warning says so. Capture builds its policy with `SecretPolicy::from_patterns(&spec.secret_patterns)` and from nothing else (ADR 0004), so a peer's capture applies the same list.

### `devcontainer.json` import, later

A `fabric env import devcontainer.json` command will map `features`, `postCreateCommand`, `remoteEnv` names and `mounts` into an `EnvSpec`. Not in v0 because v0 runs no containers and the mapping is lossy; doing it badly would be worse than not doing it.

## Alternatives considered

1. **`devcontainer.json` as the native format.** Container-shaped, large schema, and running it needs Docker or a devcontainer CLI, neither of which the first gate has. Import later instead.
2. **Nix or devenv.** Reproducible, heavy for a user who just has `pnpm` installed. The research marks devenv as reuse for toolchain reproducibility (landscape 8.1). Could become a `Tool.source` later. Not v0.
3. **Carry the whole toolchain in the snapshot** (Node binary, Rust toolchain). Huge, platform-bound, and tool managers already cache them per machine. Rejected.
4. **No spec, always run install.** Makes every resume minutes long on a warm machine. Rejected; the whole point of carrying caches is to skip this.
5. **The installer's own marker as proof of a whole `node_modules`.** Saves one reinstall after a hand install, but npm, pnpm and Yarn 1 write it before the root lifecycle scripts, so a failed `postinstall` looks whole forever. Rejected.

## Consequences

- A resume on a matching platform with a warm cache runs zero commands.
- A resume on a cold or different platform is slower but needs no user action.
- A spec is small, text, diffable and stored by content hash.
- The secret boundary is simple to audit: one struct field of names, one resolver per node.

## Open questions

- Should `fabric suspend` detect again to notice new tools, or only when no spec exists or `fabric env detect` is run? Resume always detects (step 2 of Materialize).
- How to express "this job needs a GPU" or "needs Docker"? Probably `requires: [Capability]` on the spec, consumed by placement (ADR 0008). Add when a job needs it.
- A declared step does not say which caches it fills, so it counts as filling every cache but a detected `target`. With declared steps `npm ci` and `npm run build` and a declared `.output`, a missing `.output` runs both, and `npm ci` deletes a healthy `node_modules` first. Should `[[setup]]` take a `fills` list?
- A sentinel proves that some install finished once, not that none was torn since. When the agent runs `pnpm add` or `bun add` and the harness is killed mid-install (the suspend case), the old `.fabric-installed` stays, the torn tree is carried, and the other node calls it healthy. The sentinel now records the digest of the lockfile and manifest (step 3), which catches such an install once it has rewritten either file; one killed before that still leaves the old sentinel over a torn tree. Having capture refuse while a process holds the tree would close that. Decide in the capture PR, before the gate.
- The tree lock lasts only while some process holds one of the step's two descriptors, and Node and Python pass on only the descriptors they name. npm runs dependency install scripts, such as a `node-gyp` build, with piped input, so if the installer alone is killed (the OOM killer, a force quit) while such a build still writes, the lock is released and the next resume can start `npm ci` under it. Recording the step's process group next to the lock and refusing while the group is alive closes this, but asking whether a group is alive needs a system call the standard library does not wrap, and the crates forbid `unsafe`. Decide with the CLI PR whether a small, maintained wrapper crate is worth that.
- The prompt keys on the spec id and the per-cache input digests, which are the files detection knows a step reads, and a restore of another node's snapshot asks again. On the node where the agent ran, a file the steps run that no digest covers can change between two launches without a new prompt: an edit of `scripts/setup.sh` under a declared `sh scripts/setup.sh`, or of a file a `postinstall` runs once the agent has deleted `node_modules`. A harness whose sandbox lets the agent write the workspace, as Codex's, can so run code outside that sandbox, with the network, at the next launch that runs a step. Proposal: the node removes the record when it registers a harness, so every launch that runs a step after the agent ran asks, and scripts pass `--yes`. That asks on every launch for a declared step that fills no cache, which is why it waits for the owner. Hashing the workspace files a step names as its program or arguments would cover the common declared case only.
