# Harness adapters

The contract an adapter in `crates/fabric-harness` meets, as the code has it today, and one section per adapter PR 5 adds: OpenCode, pi, Gemini CLI, Cursor Agent CLI, and GitHub Copilot CLI as a conditional last one. ADR 0006 holds the decisions behind the contract and ADR 0015 the trait as built; this page is the working reference for whoever writes or reviews an adapter. Versions and layouts below were read on 2026-11-08 from the binaries installed on the owner's Mac (OpenCode 1.18.34, pi 0.80.3, Cursor Agent CLI 2026.10.01, Claude Code 2.1.294, Codex 0.163.0), from `--help`, and from file, table, column and key names only; no transcript content was read, and every fixture in the tests is synthetic. Gemini CLI is not installed there, so its section comes from its source and documentation at v0.67.0 and its fake is built from the documented format alone.

The hard part first. Two of the four stores keep credentials beside the session: OpenCode's one SQLite file holds its login tokens next to every message, and Cursor's chat store is encrypted with the key in the same file. Fabric's invariant is that a carried file holds no file on the credential denylist and no secret-shaped string. So the OpenCode adapter carries rows the agent exports, never the file, and the Cursor adapter carries nothing of the chat until Cursor documents a format Fabric can scan. Everything else in this page follows from that invariant and from path identity (ADR 0011): a session is restored under the same workspace path and the same home, and nothing in it is rewritten.

## The contract

### The trait

`fabric_harness::Harness` (`crates/fabric-harness/src/harness.rs`) has seven methods. The core drives every adapter through them alone; no vendor type crosses the boundary.

```text
fn kind(&self) -> HarnessKind
    Which adapter this is: a variant of fabric_core::harness::HarnessKind.
fn fidelity(&self) -> Fidelity
    The highest fidelity this adapter reaches, declared once, true before any refusal.
fn detect(&self) -> Result<Option<Installed>>
    The binary on the adapter's PATH value and what it answers to --version; None when absent.
fn capture(&self, workspace, session: &SessionId, out) -> Result<StateManifest>
    Copy what `session` needs into `out`, redacted or refused, and write out/manifest.json last.
fn confirm_departure(&self, manifest) -> Result<()>
    The snapshot holding this capture is published; its departure record now counts.
fn restore(&self, workspace, state) -> Result<Restored>
    Place a captured tree on this node, all or nothing; say which session the harness continues.
fn launch(&self, workspace, Launch, env) -> Result<Running>
    Start the harness held, in a new process group, with `env` minus the parent-session markers.
```

Rules every adapter keeps:

- The session is an explicit argument. An adapter never guesses which session a job continues. A `latest_session(workspace)` helper may exist for `fabric job init` to adopt a session the user started by hand.
- The constructor takes the home as an `AbsPath` and the `PATH` value to search; the adapter never reads its own process environment except to probe a version, and that probe runs with the adapter's `PATH`. The workspace is parsed once into its physical `AbsPath`, which feeds the manifest and every path key the harness derives from the workspace.
- `capture` and `restore` run on a blocking thread through `pipeline.rs`, which owns the order of the steps and the checks; an adapter supplies its sources and, at restore, where each tree path lands and how it treats that path. Dropping their future does not stop the copy, so the caller awaits them and never launches the same session before they return.
- `launch` returns the harness held, stopped before its exec, until the caller records the pid and calls `Running::release` (ADR 0015, issue #17). A `Launch::Interactive` inherits the terminal; a `Launch::Headless` has no stdin and captured stdout and stderr, except for an agent that speaks a protocol on its stdio, whose pipes its client owns and whose turn arrives on `Running::take_turn`. A headless run cannot be built without a prompt.
- A resume carries the settings the session ran with, not the ones the node has configured (gate finding F10a): the adapter reads them from the session and passes them as typed flags, each one the adapter was configured with winning (`Origin::Pinned` over `Origin::Session`), and `Running::settings` lists what was passed (`PassedSetting`) and what was left out with why (`NotCarried`). A recorded value is cut to 64 characters with control characters replaced before anything prints it.
- Every launch runs with `env` minus the markers of a Claude Code or Codex session Fabric itself runs under (`markers.rs`), so a harness started from inside an agent's tool call is a session of its own.
- Capture and restore refuse while the harness may be writing the session (`HarnessRunning`, `ActiveWriter`), by the harness's own lock where it has one, by its process registry where it keeps one, and otherwise by any running process of that program. The ACP adapter cannot see this and leaves the guard to the caller.

### What capture must include

`capture` writes the tree under one prefix, `home/`, then `manifest.json`. The `StateManifest` holds the harness kind, the session, the physical root, the home, the harness version, the redaction counts, and every file with its tree path, its `Content` (`Opaque`, `Text`, `JsonLines`, `JsonDocument`), its `Mutability` (`AppendOnly`, `Immutable`, `Replaceable`), its length and its BLAKE3 digest. Its fields are private; a manifest comes from `StateManifest::new` or from a file, and both check the same rules: format 1, every path under `home/`, no temporary file, strictly sorted.

An adapter's sources are exactly the files the harness reads to continue the session, and nothing a second session shares. Name matching is exact: session `s1` never carries `s10.json`. A file on the denylist (`denylist.rs`: credential file names, key and database suffixes, dotenv files, credential directories, each harness's host state, Fabric's own `~/.fabric`) is refused on its tree path right before the copy, whichever adapter listed it; the list is policy, not configuration. A symlink in session state, at the store or above it under the home, refuses the capture (`SymlinkInState`). `out` belongs to the capture: a file in it that the new manifest does not list is removed before the manifest is written.

Mutability is data the adapter declares per file, and restore depends on it. `AppendOnly` is a transcript that only grows: restore accepts a destination that is missing, equal, or a byte prefix of the incoming bytes. `Immutable` is written once. `Replaceable` is rewritten in place by the harness: at capture the adapter records the digest of each such file in a pending departure record under `~/.fabric/harness/departed/<harness>/<session>.pending.json`, `confirm_departure` promotes it once the snapshot is published, and restore replaces the file only when it still holds the bytes this node recorded. A file that fails every rule is `StateDiverged`, and nothing is written. Restore also lists what a capture of the session would take on this node now, and a file on that list the incoming state does not place is removed only when the confirmed departure record says this node left it untouched.

A restore accepts only the root and home of the capture (`RootMismatch`, `HomeMismatch`), only destinations the adapter itself captures from (`UnexpectedFile`), only entries whose content and mutability match the adapter's own rule for that path (`EntryMismatch`), no destination through a symlink (`SymlinkInState`) and no two destinations that differ only in letter case (`DuplicateTreePath`). It checks every staged digest, plans every destination, and writes only when all of them pass. Every write is a temporary sibling, an fsync and a rename.

### Redaction

Two regimes exist, and an adapter picks one per file by its `Carry`:

- Redacted (`Carry::Text`, `JsonLines`, `JsonDocument`): the Claude adapter's regime. Text is redacted line by line; JSON goes through the scanner in `jsontext.rs`, which decodes every string outside a signed block, redacts it and re-encodes it. A signed block (a `thinking` block with a `signature`, or `redacted_thinking`) is never edited: one that holds a secret is dropped whole when it is an array element and counted as `signed-block-dropped`, otherwise the capture fails (`SecretInSignedBlock`).
- Refused (`Carry::OpaqueRefuseSecrets`): the Codex and ACP regime, and the one the PR 5 adapters use. Bytes travel verbatim and the capture is refused when a line holds a secret shape, on the raw line or in any JSON string literal once decoded (`SecretInState { path, line }`). A refused thread stays refused until the secret is gone from it.

The rules are in `redact.rs`: Anthropic, OpenAI, GitHub, AWS, Slack, Google and Stripe key shapes, JWTs, PEM private key blocks, `Authorization` headers, bearer tokens, credentials in URLs, and the value of an upper-case variable whose name says secret, token, password, API key, private key, access key, credentials, `DATABASE_URL` or `DSN`, except a short number under a qualified name (`MAX_TOKENS=512`). Every key rule starts on an ASCII word boundary. Launch arguments go through the same rules (`refuse_secret_args`, `SecretInArguments`), because the harness kind with its arguments is recorded in the ledger and the manifest unredacted; `--api-key sk-...` is caught joined or apart. Redaction is by pattern: it removes common key shapes, not every secret, and the README says so.

### The version guard and the writer-version rule

An older harness must not run a session a newer one wrote (gate finding F10b, ADR 0015): Codex 0.142.4 appended records without a field 0.155.1 writes, and 0.155.1 then refused the session. Before a resume starts, the adapter asks the binary it would run for its version, in the workspace and with the launch environment, and refuses when it is older than the newest version the session records or when it cannot be read (`version::refuse_older`, `HarnessOlderThanSession`, `HarnessVersionUnknown`). `Running::version` reports the version that now runs the session.

The writer-version rule says where that floor comes from. A harness that records its version on every write, as Claude does per transcript line, gives the floor from the session alone. A harness that records it only when it creates a session, as Codex does in `session_meta`, needs the node to carry the newest writer: a capture records the installed version it asked in the workspace, or the job's known writer when that is newer, in `StateManifest::harness_version`; the node keeps it as the session's known writer (`SessionRecord::known_writer`), raises it to `Running::version` after a resume, and hands it back to the adapter on the next capture (`Codex::with_known_writer`). `--force` on a move does not lower it. A PR 5 adapter states in its section which case it is, and an adapter whose format records no version at all says so and is not guarded.

Each adapter also pins the version it was read on for any vendor rule it relies on (Codex's writer lock at 0.155.1, Claude's session registry at 2.1.294) and takes the cautious path on an older or unknown binary (`version::at_least`). A PR 5 adapter pins the version its layout was read on, the ones in the first paragraph of this page, the same way.

### The fidelity declaration

`Fidelity` (`harness.rs`) has four values, with the stored names the managed continuation and the Portable Session Format use (`fabric_core::managed::package::Fidelity` on the M5 branch, ADR 0024; ADR 0029): `native_session`, `new_native_session_with_package`, `workspace_only`, `unsupported`. Nobody keeps a second vocabulary.

- `Harness::fidelity` is the declared ceiling of the adapter, true before any refusal: the README table and a client can say it without running anything. Claude Code, Codex and ACP declare `NativeSession`.
- `Restored::fidelity` is what one restore reached, never above the ceiling, and `Restored::session` is the session the harness continues on this node: the manifest's, unless the harness minted a new id when the adapter handed it the state. The node records `Restored::session` as the job's session (`restore_harness` in `fabricd`), so the next capture takes the session that actually runs, and logs the fidelity. `pipeline::restore` sets `NativeSession` and the manifest's session, because it places the harness's own files; an adapter that then imports them and gets another id back lowers both fields itself.
- An adapter never claims `NativeSession` when the id changed (decision of 2026-11-08, OpenCode). `NewNativeSessionWithPackage` is inside the default `allowed_fidelity` of the M5 branch, so a job accepts it unless it narrowed the set.
- The achieved fidelity is not yet written into the job's record: that lands with the managed continuation (PR 1 of the roadmap, M5b). Until then an adapter's roundtrip test asserts the fidelity through `Restored`, and its end-to-end row through the node's log line, which names the captured and the continued session and the fidelity when they differ.

### Features, names and where a kind appears

Each adapter is a cargo feature of `fabric-harness`, on by default: `acp`, `claude`, `codex`, and since PR 5 `opencode`, `pi`, `gemini`, `cursor`. CI builds the crate with no feature and with each one alone (`clippy -D warnings`), so a module must compile without its siblings. A kind is one variant of `fabric_core::harness::HarnessKind`, appended after the last so the postcard index of every kind a ledger holds stays what it was: `OpenCode`, `Pi`, `GeminiCli`, `CursorAgent`, displayed as `opencode`, `pi`, `gemini-cli`, `cursor-agent`. The CLI takes `--harness opencode | pi | gemini | gemini-cli | cursor | cursor-agent` (`fabricd::harnesses::parse_harness`). The client API writes `{ "kind": "opencode" | "pi" | "gemini_cli" | "cursor_agent" }`; the set of harness kinds is a closed enum of the API, so adding them bumped `API_VERSION` to 2 (ADR 0018, Compatibility rule 3), with `protocol/fixtures/closed/harness.json`, one `request/job_new_<kind>.json` per kind and the TypeScript `Harness` schema updated together. The node builds the adapter in `fabricd::harnesses::adapter` and the CLI in `fabric::adapter_for`, from the home and the `PATH` alone; none of the four reads `harness.toml`.

Until an owner builds a step, the adapter answers it with `HarnessError::NotBuilt { program, step }`, which names this page. `kind`, `fidelity` and `detect` are real from the start. The variant goes when the last adapter is built.

### Fake harnesses, e2e rows and fixtures

Every adapter is tested against a fake on `PATH` and a synthetic on-disk layout; no test touches a real session. Three shapes exist and a new adapter copies the one its harness matches:

- A shell-script fake that answers `--version` and logs its arguments, working directory and environment (`crates/fabric-harness/tests/common/mod.rs` for Claude; `fake_codex_reporting` and `fake_codex_answering` inline in `tests/codex_roundtrip.rs`, which answer `codex-cli <version>` and write argv to `$FAKE_LOG` and the environment names to `$FAKE_ENV_LOG`). Written through `tests/executable/mod.rs`, so Linux never sees `ETXTBSY`.
- A real fake agent for a protocol harness (`tests/fake_acp_agent/mod.rs`): one JSON file per session under `FAKE_STATE_DIR`, shaped by `FAKE_LOAD`, `FAKE_RESUME`, `FAKE_ASK_PERMISSION`, `FAKE_PID_FILE`, `FAKE_ENV_FILE`, `FAKE_PROMPT_ERROR` and `FAKE_LINGER`; built again as the `fabric-fake-agent` binary for the end-to-end suite.
- The end-to-end fakes in `crates/fabric/tests/e2e/world.rs` (`install_fake_claude`, `install_fake_codex`): shell scripts that keep their session files where the real harness keeps them, under the test's home, and answer the headless protocol the CLI reads.

The end-to-end suite (`crates/fabric/tests/e2e`) starts two `fabric serve` daemons on loopback, makes a job, suspends on one node and resumes on the other (`move_and_resume` in `main.rs`); `headless.rs` holds one row per harness that runs a turn without a terminal and is captured by the next suspend, and `acp_cli.rs` the ACP rows. PR 5 reserves one module per adapter, `e2e/opencode.rs`, `e2e/pi.rs`, `e2e/gemini.rs`, `e2e/cursor.rs`, and each owner installs its fake from its own module through `Env::install(name, script)`, so `world.rs` and `main.rs` are not edited twice.

Fixtures live under `crates/fabric-harness/tests/fixtures/<adapter>/` (`tests/fixtures/README.md` has the rules): the agent's real layout with synthetic content, every secret replaced by a value the redactor matches (so the refusal tests fire on it), the home written as the test's temporary home at test time, never a path from a real machine, and the version the layout was read on in a `VERSION` file beside it. An integration test `tests/<adapter>_roundtrip.rs` per adapter is reserved with its `[[test]] required-features` entry.

## OpenCode

Owner A, built. Feature `opencode`, kind `HarnessKind::OpenCode`, program `opencode`, read on 1.18.34 (`opencode::READ_ON`). OpenCode is the largest open-source harness after Claude Code and Codex (3,431,953 npm downloads in the week of 2026-11-01, 225,452 stars, 7 percent workplace use in the JetBrains 2026 survey as 36Kr reports it), and Kilo CLI vendors it (`.opencode-version` `v1.18.26` on Kilo-Org/kilocode), so the adapter serves two programs once its schema expectations are versioned.

**Session location and format.** One SQLite file, `~/.local/share/opencode/opencode.db`, in WAL mode (`opencode.db-shm`, `opencode.db-wal` beside it), holding every project: tables `session` (columns `id` with a `ses_` prefix and 30 characters, `project_id`, `workspace_id`, `parent_id`, `slug`, `directory`, `path`, `title`, `version`, `share_url`, summary and token columns, `revert`, `permission`, `agent`, `model`, times), `message` (`data` is one JSON column), `part`, `todo`, `session_message`, `session_input`, `session_context_epoch`, `session_share`, `project` (`worktree` is the absolute path), `project_directory`, `workspace`, `event`, `permission`, and the login tables `account` (`access_token`, `refresh_token`), `account_state`, `control_account` (`access_token`), `credential` (`value`), plus `session_share.secret`. `session.directory` is the absolute workspace path, which is the path key ADR 0011 keeps. Git snapshots of tool edits sit under `~/.local/share/opencode/snapshot/<hash>`; `auth.json` (mode 0600), `log/`, `repos/` and `tool-output/` are beside them.

**What `export` and `import` do on 1.18.34.** Checked on 2026-11-08 against the installed binary in an empty data directory (`XDG_DATA_HOME` and `HOME` pointed at a temporary directory) with synthetic exports only. `opencode export <id>` prints the session as pretty JSON on standard output, `{"info": {id, slug, projectID, directory, path, title, agent, model: {id, providerID, variant}, version, cost, tokens, time}, "messages": [{"info", "parts"}]}`, and `Exporting session: <id>` on standard error; an unknown id prints `Error: Session not found: <id>` and exits 1. `opencode import <file>` prints `Imported session: <id>` with the same id: the import keeps the id, so the adapter reaches `native_session`. An import of a session the store already holds keeps the stored session row and adds only the messages it lacks; it removes none. `info.directory` is stored as the physical path.

**Captured and restored.** Capture runs `opencode export <id>` itself, so Fabric never opens the database and needs no SQLite dependency. It checks that the export is the session's and that its `info.directory` is the job's physical workspace (`RootMismatch` otherwise), writes it to `~/.local/share/opencode/fabric/<id>.export.json` and stages that file as `Carry::OpaqueRefuseSecrets`, `Mutability::Replaceable`, under `home/.local/share/opencode/fabric/<id>.export.json`. The copy under `fabric/` is Fabric's own; OpenCode never reads it, and no departure record is kept for it, because restore compares the store itself. Restore first exports the session this node holds, if any. None, or a prefix of the incoming messages, goes on; the same messages need no import; anything else is work done here after the job left and is `StateDiverged`, with nothing written. It then places the file (removing an older copy of its own first) and runs `opencode import <file>`; the id it prints is `Restored::session`. On 1.18.34 an import is not atomic: it writes the session row and each message in turn and stops at the first one it refuses (an assistant message without `parentID`, `mode`, `path`, `cost` or `tokens`), keeping what it wrote, so a failed import is followed by `opencode session delete <id>`, which loses nothing because the import runs only when the node holds no more than a prefix of the incoming export, and the next restore imports into an empty store. `opencode export --sanitize` exists ("redact sensitive transcript and file data"); the adapter does not use it, because it rewrites the transcript that is meant to continue, and refuses a secret instead, as every opaque carry does. The database, its WAL, `auth.json` and the snapshot directory never travel; the denylist refuses `auth.json` and the `.db` suffix by name.

**Carried settings.** The provider and model of the last user message (`model.providerID`, `model.modelID`), else of the session row (`info.model`), passed as one `-m provider/model` and reported as `SettingName::Provider` and `Model`; the agent of the last user message, else of the session row, as `--agent`, reported under `SettingName::Agent`; the session's `info.model.variant` as `--variant`, reported as `SettingName::Effort`. Each value set with `OpenCode::with_settings` wins (`Origin::Pinned`). A recorded value that is not a plain name is not passed and is listed in `NotCarried`, as is the variant on a terminal resume, since the terminal interface takes no `--variant`.

**Headless command.** `opencode run --format json [-s <id>] [-m <provider/model>] [--agent <name>] [--variant <v>] -- <prompt>` in the workspace. Each line is `{"type", "timestamp", "sessionID", ...}` with the types `step_start`, `step_finish`, `text`, `reasoning`, `tool_use` and `error`, read on 2026-11-08 from the JavaScript the 1.18.34 binary embeds. `OpenCode::read_headless_line` takes the session from `sessionID`, the answer from the last `text` event's `part.text`, and the failure from an `error` event's `error.data.message` or `error.name`. **Resume.** `opencode run -s <id> ...` headless and `opencode -s <id> [-m ...] [--agent ...] [--prompt=<p>]` in the terminal; `--fork` is never passed.

**Achieved fidelity and why.** Declared `native_session`, reached on 1.18.34. A restore whose import prints another id reports that id in `Restored::session` and `new_native_session_with_package`, never `native_session`; the node records the new id and its log says `fidelity=new_native_session_with_package`, and the next capture takes it.

**Writer version.** The export records the OpenCode that created the session (`info.version`), stamped on the session row when it is made: `opencode import` 1.18.34 keeps whatever version the row carries (a synthetic export with `1.0.0` re-exported `1.0.0`, checked 2026-11-08), and whether a later turn restamps it was not shown. So OpenCode is the writer-version rule's second case, as Codex is: a capture records the installed version, asked in the workspace, or the job's known writer when that is newer (`OpenCode::with_known_writer`); the node keeps it as the session's known writer (`carries_known_writer` in `fabricd::ops`) and raises it to `Running::version` after a resume. Before a resume the adapter exports the session and refuses a binary older than the newer of `info.version` and the known writer (`HarnessOlderThanSession`) or one whose version cannot be read (`HarnessVersionUnknown`); `Running::version` is the version that then runs.

**Refusals.** `SecretInState` on any line of the export; `HarnessRunning` while any process holds `opencode.db` open (`lsof`, as the Codex adapter asks), since OpenCode's own writer rule has not been read from its source; `HarnessOlderThanSession` as above; `SessionNotFound` when `opencode export` says the id is unknown, and before any process starts for an id that is not `ses_` and letters and digits; `RootMismatch` for a session of another workspace; `StateDiverged` for a target that holds more than a prefix; `ConfigMoved` for a launch environment whose `XDG_DATA_HOME` is not `<home>/.local/share`. The adapter's own `export` and `import` run with `HOME` set to its home and `XDG_DATA_HOME` to `<home>/.local/share`.

**Fake harness.** `crates/fabric-harness/tests/fixtures/opencode/fake-opencode.sh`, shared by `tests/opencode_roundtrip.rs` and `crates/fabric/tests/e2e/opencode.rs`: a shell `opencode` that answers `--version` with `1.18.34`, keeps an `opencode.db` with an `account` row holding a fake token the redactor matches and a fake `auth.json`, keeps its session rows as text beside them (`fake-rows/<id>.info`, `fake-rows/<id>.msgs`), and answers `export`, `import` (a new id when `fake-new-id` exists in its data directory) and `run --format json` as 1.18.34 does; a prompt that asks for the first turn is answered from the store. e2e rows: `e2e_an_opencode_job_moves_and_resumes_without_its_database` (the session forgotten from the shared home before the resume, the first turn answered on B, `-m`, `--agent` and `--variant` carried, the fake token in neither snapshot, `fidelity=native_session` in B's log), `e2e_an_opencode_import_that_mints_an_id_is_recorded_as_a_new_session` and `e2e_an_opencode_session_that_holds_a_secret_is_refused`.

## pi

Owner A, built. Feature `pi`, kind `HarnessKind::Pi`, program `pi`, read on 0.80.3 (`pi::READ_ON`; `@earendil-works/pi-coding-agent`, author Mario Zechner, repository earendil-works/pi). Its npm count (6,148,981 a week) is inflated by products that embed the SDK; Earendil's own claim is hundreds of thousands of weekly users. It is the cleanest store of the four and the one that proves the adapter guide on a third native format.

**Session location and format.** One JSONL file per session, `~/.pi/agent/sessions/--<key>--/<ISO timestamp with : and . as ->_<uuid>.jsonl`, where the key is the workspace path without its leading `/` and with every `/`, `\` and `:` as `-` (`getDefaultSessionDirPath` in `dist/core/session-manager.js` of the installed package; for `/home/u/w` the directory is `--home-u-w--`). `PI_CODING_AGENT_DIR` moves the agent directory and `PI_CODING_AGENT_SESSION_DIR` the session directory. Version 3 of the format (`docs/session-format.md` in the installed package): a header entry `{"type":"session","version":3,"id":"<uuid>","timestamp":...,"cwd":"<workspace>"}`, then `model_change` (`provider`, `modelId`), `thinking_level_change` (`thinkingLevel`), `message` entries whose assistant messages carry `provider` and `model`, and others, forming a tree by `id` and `parentId`. An Anthropic reply carries a `thinkingSignature`, a signed block that cannot be edited.

**Captured and restored.** That one file, `Carry::OpaqueRefuseSecrets`, `Mutability::AppendOnly`, under `home/.pi/agent/sessions/<key>/<file>`. The key is derived from the physical workspace path exactly as pi derives it, and the id is matched on the whole `_<uuid>.jsonl` suffix, so a partial id never matches. The key is lossy (`/a-b` and `/a/b` share one), so the header must name the session and the workspace: another `cwd` is `RootMismatch`. Restore places the file under the same key, accepting a destination that is missing, equal, or a byte prefix of it. `auth.json`, `settings.json` and `trust.json` (documented, absent on the owner's Mac) never travel.

**Carried settings.** The provider and model of the last `model_change` or assistant message, and the level of the last `thinking_level_change`, as `SettingName::Provider`, `Model` and `Effort`, passed with `--provider <name> --model <id> --thinking <level>` (the spellings of `pi --help` on 0.80.3); each value set with `Pi::with_settings` wins.

**Headless command.** `pi -p --mode json [--session <path>] [--provider ...] [--model ...] [--thinking ...] <prompt>` in the workspace. The first line is the session header, whose `id` names the session; each `message_end` of an assistant message carries the answer in its text blocks, and `stopReason` `error` with `errorMessage` a failure (`docs/json.md` of 0.80.3). pi takes no `--`, and reads a word that starts with `-` as a flag and one that starts with `@` as a file to attach, so such a prompt is passed with one space before it. `--session-id` and `--session-dir` are not used, so pi files a new session where the adapter looks for it. **Resume.** `pi --session <path>` in the workspace, headless or in the terminal; the adapter passes the full path it found, never a partial id, which pi would also accept.

**Achieved fidelity and why.** `native_session`: the same file, byte for byte, under the same path key, and pi continues it by its own id. The header `cwd` equals the workspace, which ADR 0011 guarantees.

**Writer version.** The format records no pi version, so the version guard has no floor from the session and the manifest carries the installed version only (the writer-version rule's second case, without a known writer: nothing records which pi continued a session).

**Refusals.** `SecretInState` on any line; `HarnessRunning` while any process runs the `pi` the adapter would start, matched as a whole word of its command line by the path found and its physical path (pi takes no lock and runs as `node` with its script's path); `SessionNotFound` when no file of that id sits under the workspace's key; two files with the same uuid under one key is `LineageAmbiguous`; a header of another workspace is `RootMismatch`; a target file that is not a prefix of the incoming one is `StateDiverged`; `ConfigMoved` for a launch environment that sets `PI_CODING_AGENT_SESSION_DIR`, or `PI_CODING_AGENT_DIR` to anything but `<home>/.pi/agent`. A `sessionDir` in pi's `settings.json` is not read; a new session filed there is not found, and the capture says `SessionNotFound`.

**Fake harness.** `crates/fabric-harness/tests/fixtures/pi/fake-pi.sh`, shared by `tests/pi_roundtrip.rs` and `crates/fabric/tests/e2e/pi.rs`: a shell `pi` that answers `--version` with `0.80.3`, writes a fake `auth.json`, files a new session under the key as 0.80.3 does, appends `model_change`, `thinking_level_change` and messages with a `thinkingSignature`, prints the JSON mode's header and `message_end`, logs its arguments, and answers a question about the first turn from the file. e2e rows: `e2e_a_pi_session_moves_and_resumes_as_the_same_file` (the file removed from the shared home before the resume, the first turn answered on B, provider, model and thinking level reported as carried, the file on B the captured bytes grown, `auth.json` absent from the snapshot) and `e2e_a_pi_session_that_holds_a_secret_is_refused`.

## Gemini CLI

Owner B. Feature `gemini`, kind `HarnessKind::GeminiCli`, program `gemini`, from google-gemini/gemini-cli `main` and v0.67.0 (2026-11-04); not installed on the owner's Mac. Consumer tiers were retired on 2026-06-18 in favour of Antigravity; it stays usable with paid API keys, and its weekly downloads are down 38 percent from the June peak but rising since September (305,018 in the week of 2026-09-07 to 482,840 in the week of 2026-11-01).

**Session location and format.** Chats under `~/.gemini/tmp/<slug>/chats/`: a main session is `session-<ISO minute with : as ->-<first 8 characters of the id>.jsonl`, a name collision adds a counter, `session-<ts>-<n>-<id8>.jsonl`, and a subagent's file is `<full id>.jsonl` under `chats/<parent id>/` (`chatRecordingService.ts`, `chatRecordingTypes.ts`). The session's plans, tracker and tasks sit under `<slug>/<id>/plans`, `<slug>/<id>/tracker`, `<slug>/<id>/tasks` (`storage.ts`). The slug is `slugify(basename(project root))` with a `-<n>` suffix on collision, regex `^[a-z0-9-]+$`, assigned by the registry `~/.gemini/projects.json` and owned by a `.project_root` marker inside the slug directory that `verifySlugOwnership` checks; legacy SHA-256 directories are migrated (`projectRegistry.ts`). The published docs still say `tmp/<project_hash>/`; the code is the reference. Default cleanup deletes sessions older than 30 days, with a one-day minimum.

**Captured and restored.** The chat file resolved from the id (the 8-character prefix in the name, then the full id read from the first record, so a second session that shares the prefix is never taken), the subagent files under `chats/<id>/` and the side directory `<id>/`, all `Carry::OpaqueRefuseSecrets`; the chat and subagent files `AppendOnly` (Gemini appends every record and rewrites a chat only when it could not read it), the side directory `Replaceable` with a departure record. `projects.json` never travels: it names every project of the home, so it is neither carried nor edited. A restore places the files under the captured slug and writes the `.project_root` marker with the workspace path when it is missing; Gemini's registry, finding no entry for the workspace, takes the slug whose marker names it (`findExistingSlugForPath`) and heals its own entry. A restore is refused (`StateDiverged`, nothing written) when this node's `projects.json` gives the workspace another slug or the slug's marker names another project, since Gemini would then read another chats directory. The generic ACP adapter is not used for Gemini: with `<slug>/` as state directory it would accept the `<id>/` side directory and miss the chat file, a partial capture reported as a session. `oauth_creds.json`, `google_accounts.json`, `settings.json` and `.env` never travel; the denylist refuses the first two and the dotenv file by name.

**Carried settings.** The model of the chat's last `gemini` record (its `model` field, `chatRecordingTypes.ts`), as `SettingName::Model` with `--model`, origin `Session`; a value that is not a plain model name is reported as not carried. No other setting is recorded in a chat, and the adapter reads no `settings.json`.

**Headless command.** `gemini --output-format stream-json [--resume <id>] [--model <m>] --prompt=<text>`, the prompt joined to its flag so one that starts with `-` is never read as an option. `GeminiCli::read_headless_line` reads the stream events of `packages/core/src/output/types.ts`: `init` names the session (so a new session is recorded while the turn runs), assistant `message` events carry the answer, in pieces when `delta` is set, and a `result` with `status` `error` carries the failure. **Resume.** `gemini --resume <id>` in the workspace, interactive, with `--prompt-interactive=<text>` when there is a first message. ACP (`gemini --acp`, `session/load`) is not used: the headless and terminal paths reach the same session with the CLI's own flags, and the fake stays a shell script.

**Achieved fidelity and why.** `native_session`: the chat file is continued by `--resume` under its own id, once the marker is in place.

**Refusals.** `SecretInState` on any line; `SessionNotFound` when no chat file of the workspace's slug names the id; two chat files whose first record names the id are `LineageAmbiguous`; `StateDiverged` as above; `HarnessRunning` at capture and restore while any `gemini` runs, by name or by the binary's path on a command line (Gemini takes no lock on a chat); `HarnessOlderThanSession` and `HarnessVersionUnknown` from the version guard below.

**Version guard.** A chat records no Gemini version, so the adapter is the writer-version rule's second case, as Codex is: a capture records the installed version, asked in the workspace, or the job's known writer when that is newer (`GeminiCli::with_known_writer`); the node keeps it as the session's known writer (`carries_known_writer` in `fabricd::ops`), raises it to `Running::version` after a resume, and a resume refuses a `gemini` older than it before anything starts. A session never captured has no known writer and is not guarded. The layout is pinned at `READ_ON` 0.67.0.

**Fake harness.** `tests/gemini_roundtrip.rs` copies the synthetic fixture under `tests/fixtures/gemini/` (a chat, a second chat sharing its prefix, a subagent file, plans and a tracker, a registry, a marker and fake login files) into a temporary home, with a shell `gemini` that answers `--version` and logs its arguments. The end-to-end fake in `crates/fabric/tests/e2e/gemini.rs` writes the same layout as it runs and answers a question about the first turn from the chat it resumes. e2e rows: `e2e_a_gemini_session_found_by_its_short_id_moves_and_answers_about_its_first_turn` (capture takes the chat and its plan and not the prefix-sharing session, the target never ran Gemini, the resumed turn answers about the first turn under the same id and model, and the node logs `native_session`) and `e2e_an_older_gemini_is_refused_a_session_a_newer_one_continued`.

## Cursor Agent CLI

Owner B. Feature `cursor`, kind `HarnessKind::CursorAgent`, program `cursor-agent` (also installed as `agent`), read on 2026.10.01-e373342. Blocked on format, not on code: the decision of 2026-11-08 is `workspace_only` by default.

**Session location and format.** A headless or interactive chat lives in `~/.cursor/chats/<md5 of the workspace path>/<chat id>/`: `meta.json` (`createdAtMs`, `cwd`, `hasConversation`, `schemaVersion`, `updatedAtMs`, sometimes `title`), `prompt_history.json`, and `store.db` with `store.db-shm` and `store.db-wal`. `store.db` has exactly two tables, `blobs(id TEXT PRIMARY KEY, data BLOB)` with 64-hex content-addressed ids and encrypted data, and `meta(key TEXT PRIMARY KEY, value TEXT)` with one row, key `0`, whose value is hex-encoded JSON with `agentId`, `blobEncryptionKey`, `createdAt`, `isRunEverything`, `latestRootBlobId`, `mode`, `name` and often `subagentInfo`. Eleven of fifteen stores on the owner's Mac could not be opened read-only while their WAL existed and needed `immutable=1`. An ACP session (`cursor-agent acp`) leaves only `~/.cursor/acp-sessions/<id>/meta.json` with `cwd` and `schemaVersion` 1, and none of the eight ACP session ids there appears under `chats/`: the ACP transcript is server-side or in memory. `cli-config.json` holds `authInfo`, `model`, `permissions`, `sandbox` and `approvalMode`.

**Captured and restored.** Nothing of the chat. The encrypted blobs cannot be scanned for the invariant, decrypting them would mean parsing a private format with its key, and the ACP path has no local transcript. The adapter's `capture` succeeds with an empty file list and a manifest that names the session, the installed version, and the reason in its redaction counts (`cursor-store-not-carried`), so a move still carries the workspace and the job's record; `restore` places nothing, refuses a tree that lists any file (`UnexpectedFile`), and reports `Restored::fidelity` `WorkspaceOnly` with the manifest's session. `cli-config.json` and the chat directories never travel.

**Carried settings.** None. Nothing is read from the store, and the adapter has no configuration of its own yet, so a model, `--sandbox` or `--mode` is Cursor's own on each node. A resume on a node that does not hold the chat reports it under `SettingName::Chat` as not carried, with the reason, so the user is told the conversation stayed behind.

**Headless command.** `cursor-agent --print --output-format stream-json --trust [--resume <chat id>] -- <prompt>` in the workspace (`--trust`, because the workspace is the job's own; `--` ends the options, so a prompt that starts with `-` is never read as one). `CursorAgent::read_headless_line` reads the stream of Cursor's output format reference (read 2026-11-08): every event names `session_id`, so a new chat is recorded while the turn runs; an `assistant` event carries a whole message; the `result` event carries the full text, or the failure when `is_error` is set or `subtype` is not `success`. **Resume.** `--resume <chat id>` only when this node holds that chat, a `~/.cursor/chats/<hash>/<id>/` directory with a `store.db`; a moved job by definition does not, so the resume starts a new chat in the restored workspace. Interactive is the same without `--print`.

**Achieved fidelity and why.** Declared and reached `workspace_only`. The ACP case would be `new_native_session_with_package` at best, a new ACP session handed the package, and is dropped from PR 5: the package does not exist on this branch.

**Refusals.** `HarnessRunning` at capture while a process holds the chat's `store.db` or its WAL open (`lsof`), since the session then still runs on this node. The guard looks at the open store and not at the program name, because Cursor's editor runs `cursor-agent` workers of its own that never touch the chat; one ran on the owner's Mac when this was written. `UnexpectedFile` at restore for any listed file. The Cursor kind has no launch arguments, so there is nothing for `refuse_secret_args` to check, and the adapter never passes `--api-key`. A job that narrows `allowed_fidelity` to `native_session` is refused by the managed continuation once M5b lands, not by this adapter.

**Version guard.** None applies: nothing of the session travels, and a chat continued with `--resume` is one this node's own `cursor-agent` wrote. The manifest still records the installed version. The layout is pinned at `READ_ON` 2026.10.01-e373342.

**Fake harness.** `tests/cursor_roundtrip.rs` copies the synthetic fixture under `tests/fixtures/cursor/` (a chat with a `store.db` that holds a fake key, its `meta.json`, an ACP session's `meta.json`, a `cli-config.json`), naming the chat directory by the md5 of the test's workspace, which the system's `md5` or `md5sum` computes, with a shell `cursor-agent` that answers `--version` and logs its arguments. The end-to-end fake in `crates/fabric/tests/e2e/cursor.rs` writes the same layout, leaves `NOTES.md` in the workspace on its first turn, and answers a question about the first turn from that file. e2e row: `e2e_a_cursor_job_moves_as_its_workspace_and_a_new_chat_answers_from_it`: a suspend is refused while a `cursor-agent` holds the chat open; then the snapshot holds no byte of the store or the login, the target starts a new chat and says the old one stayed behind, the question about the first turn is answered there from the workspace, and the node logs `workspace_only`.
