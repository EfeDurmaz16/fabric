# Checks that need the second Mac

Written 2026-11-03, when `main` (merge of PR #32) was walked on one Mac ([usable-from-main/walk.md](usable-from-main/walk.md)). Everything below needs two real hosts with the same user name and home (ADR 0011), and the second Mac was off that night, so none of it ran. Each row says what is checked and the commands that check it. Build once and copy the binary (README, Two Macs, by hand); the node on each Mac is `fabric serve` started from that Mac's desktop session, not over SSH, so it can read the Keychain.

Pair first, on both Macs, and keep the ids:

```sh
fabric node id                                   # on each Mac
fabric node add fab1<air-id> <air-address>:7777  # on the Pro
fabric node add fab1<pro-id>                     # on the Air
fabric node ping fab1<air-id> && fabric doctor --peer fab1<air-id>   # on the Pro
```

| Gate | What must hold | Commands |
|---|---|---|
| G1 Codex across two Macs | A Codex job answers a turn on the Pro, is suspended and moved, resumes on the Air and answers a question about its first turn; the workspace on the Air equals the source (`git status`, staged and unstaged diffs, untracked files, carried caches); `.env` stays behind; the resume carries the thread's model, provider, effort and sandbox (gate finding F10); the job comes back. The 2026-10-21 run did this on the binary of that day; it has not been run on `main` since M2 and M3 merged. | On the Pro: `fabric job new --repo <repo> --goal "..." --harness codex`, `fabric job run <job> --headless --prompt "Say hello and name one file here."`, make an uncommitted change and an untracked file, `fabric job suspend <job>`, `fabric job move <job> --to fab1<air-id>`. On the Air: `fabric job resume <job> --headless --prompt "Which file did you name before?"`, `git -C ~/fabric/jobs/<job>/work status --porcelain`, `fabric job status <job>`. Back on the Pro: `fabric job resume <job>`, `fabric job log <job>`. |
| G2 Claude Code across two Macs | The same walk under `--harness claude`: the transcript is captured, moved and continued on the Air with the transcript's model; `doctor --peer` refuses a Claude version mismatch and `--force` waives it with its row printed; no `claude` runs on the Air during the resume (ADR 0015, Claude older than 2.1.294). Claude Code has never been run across two machines. | Both Macs: `claude login` in the shell that starts the node, or start the node from the desktop session, and `fabric doctor` must say `claude.login: yes`. Then the G1 commands with `--harness claude` and prompts of the same shape, plus `fabric doctor --peer fab1<air-id> --job <job>` before the move. |
| G3 Timings | Suspend, move, and resume plus one headless turn on the other Mac, each timed, against the README's table (0.85 s, 1.15 s, 6 s on 2026-10-21) and the performance rule (CONTRIBUTING: no hot path slower than anchor `176622e`). The one-host A/B bench runs on one Mac; the cross-host numbers need the link. | On the Pro: `time fabric job suspend <job>`, `time fabric job move <job> --to fab1<air-id>`. On the Air: `time fabric job resume <job> --headless --prompt "..."`. Same job under Codex and under Claude; `FABRIC_LOG=debug` on both nodes for the per-step lines; record the numbers beside the 2026-10-21 table in the README. |
| M5 Cross-host placement | Not on `main` yet (PR from `m5/placement-continuity`). Once merged: a managed job submitted on one Mac is placed on the other by the deterministic ranking (ADR 0026: filters on platform, harness inventory, path layout, free disk; then current placement, warmth, load, identity), a node that does not answer within 5 s is ineligible, and a submit with no eligible node is parked with its exclusions; the facade (ADR 0027) answers `inspect` and `watch` from the other node with a token scoped to the job. | The M5 PR names the commands; the shape its decisions fix is: on the Pro, `fabric managed create ... --operation-key <k>` with a requirement only the Air meets (a harness installed only there), then `fabric managed status <job>` on both Macs; stop the Air's node and submit again to see the parked state with exclusions; mint a facade token on the authority and run `inspect` and `watch` from the other Mac. Record the placement decision lines and the parked exclusions. |
| M6 Real two-host partition | Not on `main` yet (PR from `m6/loss-recovery`). Once merged: with the attempt running on the Air and the authority on the Pro, cut the link (Wi-Fi off on the Air, or a firewall rule), the authority marks the resource unavailable after the heartbeat gap and, under `restart_from_acknowledged` with an acknowledged checkpoint, regrants on the Pro; the old attempt, woken when the link returns, is fenced on every covered write (ledger append, bundle publish, journal operation, facade outcome) at its stale generation; under the default `block` policy the job waits with its state visible. The merged proof runs two daemons on one Mac through a pausable relay; this is the same with a real link. | After the M5 and M6 PRs: place a managed job on the Air with a harness attempt running, `fabric managed status <job>` on the Pro to see the acknowledged checkpoint, cut the Air's network, watch `fabric managed status <job>` on the Pro until the resource is unavailable and, under `restart_from_acknowledged`, a new attempt is granted; restore the network and read `fabric managed status <job>` and the journal on both Macs: the Air's attempt must be fenced, never a second live writer. Repeat with `kill -STOP` and `kill -CONT` of the Air's harness, and with `kill -9` of the Air's node. |

Two more rows are not gates but should be recorded in the same session: the network change of gate finding F3 (`fabric node add` again with the new address after the Pro changes subnet), and a `move` whose target is stopped between `MoveStarted` and the answer, to see the job frozen on the source until the target returns (ADR 0003, no `move --abort` yet).
