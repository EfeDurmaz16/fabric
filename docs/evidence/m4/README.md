## Review round: who settles a dispatched operation

Five findings against the M4 head, each verified on the code before anything changed. The regression tests named here failed first, on the assertion the finding predicted, with the client's change stashed.

| Finding | Verdict | What changed |
|---|---|---|
| A request whose caller stopped waiting never becomes `unknown`: Drop only removed the waiter, a later loss drained the waiters only, so the row stayed `dispatched` until a restart and the create guard, `attach`, `cleanup` and `residuals` all missed it | real | `765917c`: Drop marks the request due and the next call handed the log records it `unknown`, as at its deadline, before the late locators. `tests/process.rs` `a_late_answer_records_the_locator_it_names_and_not_its_status` and `tests/off_runtime.rs` `a_caller_that_stops_waiting_on_the_log_leaves_the_operation_recorded_and_sent` now pin `unknown`, the guard's refusal of the next create, the residual, and the observe that settles it; `tests/stream.rs` `a_request_whose_caller_stopped_waiting_is_unknown_once_the_worker_is_lost` pins the status after a loss |
| `settle()` moved a `dispatched` exec to `unknown` on an observe answered `unknown`/`observation_failed` while the request was in flight, then refused the request's own refusal as a transition, leaving an `ExecMayRun` blocker for an exec that never ran | real | `d05a117`: the bridge keeps the operations whose request is in flight on it; an observe of one that learned nothing, or was lost or timed out, changes nothing. With no request in flight the M3 rule stands (`exec_observe_after_worker_loss`: an exec answered `running` and observed through a new worker becomes `unknown`), which is why the fix is not "reads never move `dispatched`". `tests/stream.rs` `an_observe_that_learned_nothing_leaves_a_dispatched_request_to_its_answer` drives the exact order against a scripted worker |
| Fabric CI pinned the Capsule M3 worker (`a4d597a`) although the M4 interop tests send `attach` | real, fixed before this round | `f480682` moved both jobs to Capsule `ee189d4`, the worker the interop runs above used; Capsule's `m4/reconciliation` must be pushed before those jobs can fetch it |
| A destroy refused `provider_failed`/`not_found` on a target that is already gone is recorded `failed`, a `StopNotConfirmed` blocker with no exit: every later destroy of it is `not_found` again, abandoning never unblocks, a terminal row cannot be observed, and the create stays a residual | real, blocked on a decision | Two findings describe the same dead end. The worker's `prepare` (Capsule `dispatch.ts`) refuses before any effect when the target does not exist in the bound scope, while its observe of a destroy treats a missing target as terminal and answers `completed`. The exit needs either the worker to answer a destroy of an absent target in its bound scope `completed` (idempotent destroy; the risk is a destroy sent to the wrong engine succeeding while the container runs elsewhere, the same risk the observe path already carries) or an owner-approved "confirmed gone" acknowledgement recorded as an exit from `StopNotConfirmed`. Either is a v1 protocol or journal rule change with a fixture, so it goes in lockstep across both repos once Efe chooses; nothing was changed here |

Hot paths touched: `InFlight::next` takes one more lock (the open set) per read answer, and `Drop` one more insert; `catch_up` makes no log call when nothing is due, as `record_found` did, so `tests/off_runtime.rs` still pins the same thread hop counts. Nothing was timed.
